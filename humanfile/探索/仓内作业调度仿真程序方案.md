# 仓内作业调度仿真程序方案

## 结论

建议把仓内作业调度实现为一个**离散事件仿真程序**：以入库单、出库单等 L1 业务单据为输入，依据仓内作业节点编排生成 L2 工序单据，再将工序单据拆成 L3 任务单据；调度器在库存、库位、人员、设备、通道、时间窗和休息时段约束下推进事件，最终同时输出单据、工序、任务、资源、空间和瓶颈结果。

```text
L1 业务单据
  → 节点编排
  → L2 工序单据
  → L3 任务单据
  → 资源与空间约束下的事件调度
  → 状态回写与结果统计
```

程序第一版只解决一条可验证闭环：

```text
入库单 / 出库单
→ 节点判断
→ 工序单据生成
→ 任务拆分
→ 库存与位置预占
→ 任务调度
→ 作业完成
→ 工序、单据和资源状态回写
→ 结果输出
```

本方案与同目录的《场景模拟基础资料》和《有限空间资源约束下的仓内作业调度模型》配套使用：前者提供仓库、单据和营业日场景，后者提供瓶颈、准入、资源组合和评分原则，本方案把这些规则落成可执行的程序结构。

---

## 1. 程序边界

程序只负责在给定场景和规则下重放仓内作业过程，并输出可追溯的计算结果；不负责保存业务主数据，也不负责连接真实设备或外部系统。

### 1.1 第一版范围

| 范围 | 第一版支持内容 |
|---|---|
| 业务单据 | 入库单、出库单、单据明细、单据状态、计划时间、优先级 |
| 仓内节点 | 到货签收、质检、装容器、上架、补货、拣货、复核播种、增值加工、打包装箱、组包/集包、出库交接 |
| 库存位置 | 收货暂存、储备托盘库位、储备箱格库位、拣选位、集货位、出库暂存位 |
| 执行资源 | 叉车、拣货人员、发运动作位、主通道/窄巷道 |
| 时间模型 | 营业时段、休息时段、任务标准作业时长、事件发生时间、截止时间 |
| 调度规则 | 硬约束、预占、授权预算、优先级、截止时间、路径和资源评分 |
| 输出结果 | 单据链路、节点状态、任务状态、资源利用、空间峰值、阻塞和瓶颈 |

### 1.2 第一版不纳入的内容

以下内容不进入第一版计算闭环：真实设备指令、真实库存账务、跨仓调拨、供应商接口、运输承运商接口、复杂路线优化、预测模型和长期排班优化。

这些内容可以在程序边界稳定后作为输入适配器或策略模块增加，不改变 L1 → L2 → L3 的核心分层。

## 2. 输入设计

输入必须同时描述业务、仓内结构、当前状态、作业编排、资源、事件和调度策略；只输入任务清单无法计算单据状态和节点跳过结果。

### 2.1 输入文件组织

建议使用 YAML 作为场景编辑格式，程序启动时解析为内部对象；需要交换或批量生成时可导出 JSON。

```text
scenario/
├── warehouse.yaml       # 仓库、营业日和营业时段
├── locations.yaml       # 区域、货架、库位、缓冲位、通道
├── inventory.yaml       # 初始库存、容器和库存状态
├── documents.yaml       # L1 入库单、出库单及明细
├── process-routes.yaml  # 作业节点编排和跳过条件
├── resources.yaml       # 叉车、拣货人员、工作位、共享通道
├── events.yaml          # 到货、发运、订单释放等外部事件
└── policies.yaml        # 容量、预占、评分和降级策略
```

一套场景必须能通过一个入口文件引用以上数据，保证仿真可重复运行：

```yaml
scenario:
  code: WMS-SIM-20261111-001
  warehouse: warehouse.yaml
  locations: locations.yaml
  inventory: inventory.yaml
  documents: documents.yaml
  processRoutes: process-routes.yaml
  resources: resources.yaml
  events: events.yaml
  policies: policies.yaml
  seed: 20261111
```

### 2.2 仓库、时段与位置

仓库输入描述面积、营业时段和事件处理方式；位置输入必须下沉到可占用的具体库位，不能只保留“储备区”或“拣货区”这种区域级容量。

```yaml
warehouse:
  code: WH-001
  area: 1000
  businessDate: 2026-11-11
  shifts:
    - code: S1
      start: "08:30"
      end: "12:00"
    - code: S2
      start: "13:00"
      end: "18:00"
    - code: S3
      start: "18:30"
      end: "22:00"
  breaks:
    - start: "12:00"
      end: "13:00"
    - start: "18:00"
      end: "18:30"
  breakPolicy: queue-events-and-resume
```

位置对象至少包含以下字段：

```yaml
locations:
  - code: SZ-A-R01-C01-L01
    zone: SZ-A
    type: pallet_location
    rack: R01
    column: C01
    level: L01
    capacity:
      pallet: 1
    occupied:
      pallet: 1
    reserved:
      pallet: 0
    status: available

  - code: SZ-A-R01-C03-L02
    zone: SZ-A
    type: carton_location
    rack: R01
    column: C03
    level: L02
    capacity:
      carton: 8
    occupied:
      carton: 5
    reserved:
      carton: 0
    status: available

  - code: PK-01-BIN-001
    zone: PK-01
    type: picking_location
    capacity:
      carton: 6
      piece: 120
    occupied:
      carton: 3
      piece: 60
    reserved:
      carton: 0
      piece: 0
    status: available
```

位置容量按位置类型独立计算：

```text
pallet_location  → 托盘位
carton_location  → 箱格位或料箱位
picking_location → 拣选位的箱、件容量
staging_location → 暂存位或集货位
lane             → 同时通行数量
```

托盘库位、箱格库位、拣选位和暂存位不得合并成一个容量池。

### 2.3 初始库存

库存是任务可执行性的前置状态，必须记录容器、位置和可用数量；程序不得从出库任务数量反推库存存在。

```yaml
inventory:
  - inventoryId: INV-000001
    owner: OWNER-001
    sku: SKU-001
    skuName: 商品001
    batchNo: B20261101
    qualityStatus: available
    containerType: pallet
    quantity: 1
    unit: pallet
    location: SZ-A-R01-C01-L01
    availableQty: 1
    lockedQty: 0

  - inventoryId: INV-000002
    owner: OWNER-001
    sku: SKU-001
    skuName: 商品001
    batchNo: B20261101
    qualityStatus: available
    containerType: carton
    quantity: 5
    unit: carton
    location: SZ-A-R01-C03-L02
    availableQty: 5
    lockedQty: 0
```

库存校验至少覆盖货主、SKU、批次、质量状态、容器类型、数量、所在位置、可用数量和锁定数量。

### 2.4 L1 业务单据

入库和出库必须以业务单据进入仿真；任务不能代替单据作为程序输入。

```yaml
documents:
  - docNo: INB-20261111-0001
    docType: inbound
    inboundType: purchase
    warehouse: WH-001
    owner: OWNER-001
    sourceNo: PO-20261111-0001
    status: released
    planTime: "08:30"
    priority: 3
    lines:
      - lineNo: 1
        sku: SKU-001
        planQty: 1200
        unit: piece
        batchNo: B20261101
        arrivalContainerType: carton
        targetContainerType: carton
        needQc: true
        crossDock: false
        targetZone: SZ-A

  - docNo: OUT-20261111-0001
    docType: outbound
    outboundType: sales
    warehouse: WH-001
    owner: OWNER-001
    sourceNo: SO-20261111-0001
    status: released
    planTime: "08:30"
    priority: 4
    lines:
      - lineNo: 1
        sku: SKU-001
        planQty: 60
        unit: piece
        batchNo: B20261101
        pickingMode: piece
        needCheck: true
        needValueAdded: false
        needPack: true
        needConsolidation: false
```

场景模拟基础资料中的基线规模为 `30` 张入库单、`48` 张出库单，共 `78` 张 L1 业务单据。程序应支持批量生成完整数据，同时保留少量固定样例用于复核。

L1 单据最少包含以下字段：

| 数据组 | 字段 | 作用 |
|---|---|---|
| 单据头 | `docNo`、`docType`、`warehouse`、`owner`、`sourceNo`、`status` | 识别业务单据及其来源 |
| 时间优先级 | `planTime`、`priority`、`dueTime` | 决定释放和调度顺序 |
| 明细行 | `lineNo`、`sku`、`planQty`、`unit`、`batchNo` | 形成库存与任务数量守恒关系 |
| 业务属性 | `needQc`、`crossDock`、`pickingMode`、`needCheck`、`needPack`、`needConsolidation` | 决定节点是否需要生成 |

### 2.5 作业节点编排

节点编排决定一张 L1 单据要经过哪些仓内工序；必需节点生成 L2 工序单据，可跳过节点只记录跳过原因，不生成占位工序单据或任务。

```yaml
processRoutes:
  inbound:
    - processCode: NODE-RECV
      nodeName: 到货签收
      sequence: 10
      required: true
      taskPrefix: RCV

    - processCode: NODE-QC
      nodeName: 质检
      sequence: 20
      requiredWhen: "needQc == true"
      taskPrefix: QC

    - processCode: NODE-PKG
      nodeName: 装容器
      sequence: 30
      requiredWhen: "arrivalContainerType != targetContainerType"
      taskPrefix: PKG

    - processCode: NODE-SHELF
      nodeName: 上架
      sequence: 40
      requiredWhen: "crossDock != true"
      taskPrefix: PUT

  outbound:
    - processCode: NODE-REPLENISH
      nodeName: 补货
      sequence: 10
      requiredWhen: "pickingAvailableQuantity < demandQuantity"
      taskPrefix: RPL

    - processCode: NODE-PICK
      nodeName: 拣货
      sequence: 20
      requiredWhen: "pickingMode != 'pallet'"
      taskPrefix: PICK

    - processCode: NODE-CHECK
      nodeName: 复核播种
      sequence: 30
      requiredWhen: "needCheck == true"
      taskPrefix: CHECK

    - processCode: NODE-VALUE
      nodeName: 增值加工
      sequence: 40
      requiredWhen: "needValueAdded == true"
      taskPrefix: VALUE

    - processCode: NODE-PACK
      nodeName: 打包装箱
      sequence: 50
      requiredWhen: "needPack == true and pickingMode != 'pallet'"
      taskPrefix: PACK

    - processCode: NODE-SET
      nodeName: 组包/集包
      sequence: 60
      requiredWhen: "needConsolidation == true"
      taskPrefix: SET

    - processCode: NODE-HANDOVER
      nodeName: 出库交接
      sequence: 90
      required: true
      taskPrefix: HND
```

节点判定输出必须包含完整结果：

```json
{
  "docNo": "OUT-20261111-0002",
  "processCode": "NODE-PICK",
  "decision": "skipped",
  "skipReason": "整托出库",
  "processDocNo": null,
  "taskCount": 0
}
```

跳过原因限定为已定义的业务原因：

| 节点 | 跳过原因 |
|---|---|
| 质检 | 供应商免检、货物类型免检 |
| 装容器 | 目标容器已匹配 |
| 上架 | 越库转运 |
| 补货 | 拣选位库存足够 |
| 拣货 | 整托出库 |
| 复核播种 | 整托出库且无需拆分 |
| 增值加工 | 普通订单无需加工 |
| 打包装箱 | 整托出库、已完成标准包装 |
| 组包/集包 | 单包裹直接交接 |

### 2.6 资源与策略

资源输入描述每个执行单元的能力、可用时间和当前位置；策略输入描述硬约束、预算和评分参数。

```yaml
resources:
  - resourceId: F-01
    resourceType: forklift
    capabilities: [pallet, carton]
    status: available
    location: RCV-01
    workWindows: [S1, S2, S3]

  - resourceId: P-01
    resourceType: picker
    capabilities: [piece, carton]
    status: available
    location: PK-01
    workWindows: [S1, S2, S3]

  - resourceId: A-01
    resourceType: shared_lane
    capacity: 1
    status: available
    allowedModes: [forklift]
```

策略按以下顺序执行：

```text
硬约束过滤
→ 位置、库存和资源预占
→ 授权预算判断
→ 截止时间判断
→ 路径和资源评分
→ 选择下一项任务
```

策略必须可配置并带版本号：

```yaml
policy:
  code: budget-reservation-score
  version: 1
  maxWip:
    RB-01: 12
    PK-01: 24
    CB-01: 10
    SB-01: 10
  scoreWeights:
    priority: 0.35
    dueTime: 0.25
    bottleneckProtection: 0.20
    travelCost: 0.10
    loadEfficiency: 0.10
```

## 3. 内部对象与状态

程序内部对象必须保持 L1、L2、L3 的父子关系，任务完成后逐层回写；任何层级都不能脱离父级单独推进业务完成状态。

### 3.1 L1 业务单据

L1 表示外部业务要求，负责承载业务数量、来源、时效、货主和节点编排结果。

```text
L1Document
├── docNo
├── docType
├── lines[]
├── routePlan[]
├── processDocs[]
├── status
└── auditTrail[]
```

### 3.2 L2 工序单据

L2 表示一个作业批次的一道工序，允许一张 L2 承接多张 L1，也允许一张 L1 被拆到多个 L2。

```text
ProcessDocument
├── processDocNo
├── processCode
├── batchNo
├── sourceDocNos[]
├── lineRefs[]
├── sequence
├── status
├── required
├── skipReason
├── tasks[]
└── auditTrail[]
```

L2 生成规则为：

```text
L2 = 作业批次 × processCode × 可执行明细集合
```

当节点被跳过时：

```text
required = false
processDocNo = null
taskCount = 0
skipReason = 已登记的业务原因
```

### 3.3 L3 任务单据

L3 表示一个执行单元的一次动作，必须可以追溯到 L2 和 L1。

```text
TaskDocument
├── taskNo
├── processDocNo
├── sourceDocNo
├── taskType
├── sourceLocation
├── targetLocation
├── quantity
├── unit
├── requiredResource
├── earliestStart
├── dueTime
├── status
├── reservation
└── auditTrail[]
```

不同节点采用不同拆分单位：

| 节点 | L3 拆分单位 | 主要资源 |
|---|---|---|
| 到货签收 | 到货托盘或料箱 | 收货作业位、叉车 |
| 质检 | 质检批次和明细行 | 质检人员、质检位 |
| 装容器 | 托盘或料箱 | 叉车、容器 |
| 上架 | 目标库位 × 托盘或料箱 | 叉车、窄巷道 |
| 补货 | SKU × 拣选位 × 补货箱 | 叉车、窄巷道 |
| 拣货 | 订单 × 明细行 × 拣货容器 | 拣货人员 |
| 复核播种 | 周转箱或订单容器 | 复核位、人员 |
| 增值加工 | 加工批次和容器 | 加工位、人员 |
| 打包装箱 | 包裹或箱 | 包装位、人员 |
| 组包/集包 | 周转箱、托盘或车次 | 集货位、叉车 |
| 出库交接 | 出库容器 × 发运位 | 发运动作位、叉车 |

### 3.4 状态模型

状态只允许按定义的迁移推进；被跳过的节点进入 `skipped`，不进入 `completed`。

```text
L1：draft → released → processing → partial_completed → completed
                         └────────→ blocked
                         └────────→ cancelled

L2：created → ready → released → processing → completed
       └──────────────────────→ skipped
       └──────────────────────→ blocked

L3：created → waiting → reserved → ready → running → completed
       └────────────────────────────────────────→ blocked
       └────────────────────────────────────────→ cancelled
```

状态推进条件：

| 层级 | 完成条件 |
|---|---|
| L3 | 执行数量完成，实际库存和位置变化已提交，资源预占已释放 |
| L2 | 其下所有 L3 完成；或者节点被判定为跳过 |
| L1 | 所有必需 L2 完成，跳过 L2 已登记原因，单据数量完成 |

## 4. 仿真执行流程

仿真按离散事件推进，不按固定分钟循环扫描全部任务；每次事件只更新受影响的单据、节点、任务、资源、库存和位置。

### 4.1 初始化与校验

程序先校验输入，校验不通过时不进入仿真。

必须校验：

1. 单据编号、工序单号、任务编号不重复；
2. SKU、货主、批次、位置和资源引用存在；
3. 库位类型、容器类型和库存单位匹配；
4. 初始库存的可用数量不小于锁定数量；
5. 出库需求不超过可用库存与可补货库存；
6. 节点 `processCode` 已注册且序号不重复；
7. 所需资源具备节点要求的能力；
8. 任务时间窗落在营业时段内；
9. 休息时段不产生新的执行区间；
10. 单容量通道的容量为正数；
11. 位置容量、预占数量和实际占用数量均不为负；
12. 单据明细数量、工序数量和任务数量可以逐级核对。

校验结果分为三类：

```text
error   → 不允许启动仿真
warning → 允许启动，但写入运行报告
info    → 写入校验记录
```

### 4.2 L1 到 L2 的派生

单据释放后，程序读取节点编排并为每个节点生成判定记录：

```text
L1 释放
→ 读取适用的 route
→ 按单据属性判断 required / skipped
→ 对 required 节点按批次创建 L2
→ 对 skipped 节点登记 skipReason
→ 等待前置 L2 满足依赖
```

L2 不应在启动时全部变成可执行任务。只有前置工序完成、库存满足、位置可用和资源窗口存在时，L2 才进入 `ready`。

### 4.3 L2 到 L3 的派生

L2 进入 `ready` 后，程序按照节点拆分规则创建 L3：

```text
上架：目标库位 × 容器
补货：SKU × 拣选位 × 箱
拣货：订单 × 明细行 × 拣货容器
集货：周转箱 × 集货位
出库交接：出库容器 × 发运位
```

创建 L3 时先计算预占需求，再决定是否进入调度候选集：

```text
可执行 = 库存可用
       × 目标位置可用
       × 资源可用
       × 路径可达
       × 营业时间可用
       × 前置工序已完成
```

预占必须同时覆盖库存、目标位置、执行资源和共享通道；任务取消或阻塞时释放未使用的预占。

### 4.4 事件队列

事件队列按事件时间、事件优先级和序号排序，保证同一时间的处理顺序稳定。

```text
事件时间
→ 系统事件优先级
→ 任务完成
→ 资源释放
→ 位置释放
→ 业务单据释放
→ 新任务生成
→ 调度决策
```

第一版事件类型：

| 事件 | 触发结果 |
|---|---|
| `DOCUMENT_RELEASED` | L1 进入节点判定 |
| `ARRIVAL_RECEIVED` | 入库单到货数量进入收货暂存 |
| `SHIPMENT_COMPLETED` | 出库暂存和发运位释放 |
| `PROCESS_CREATED` | 创建 L2 工序单据 |
| `TASK_CREATED` | 创建 L3 任务并计算预占 |
| `TASK_STARTED` | 锁定执行资源和路径资源 |
| `TASK_COMPLETED` | 提交库存、位置和容器变化 |
| `BREAK_STARTED` | 暂停新任务启动，保留进行中任务规则 |
| `BREAK_ENDED` | 处理队列事件并恢复调度 |
| `RESOURCE_BLOCKED` | 资源进入不可用状态并重算候选集 |

### 4.5 调度决策

调度器每次只从满足硬约束的候选任务中选择下一项，不把“资源空闲”直接当成“任务可执行”。

```text
候选任务
→ 硬约束过滤
→ 预占冲突过滤
→ 授权预算过滤
→ 截止时间过滤
→ 评分排序
→ 选中任务
→ 写入决策日志
```

硬约束包括：

- 库存不能变为负数；
- 位置实际占用加预占不得超过对应容量；
- 托盘、箱、件不能跨越不匹配的位置类型；
- 同一库存、资源或通道不能重复预占；
- 同一资源同一时间不能执行两个任务；
- 单容量主通道同一时间只能服务一台叉车；
- 休息时段不启动新任务；
- 营业日结束前无法完成的任务不再释放；
- 前置 L2 未完成时不得生成后续节点任务。

候选任务通过硬约束后，按目标函数评分：

```text
score(task) =
    w_priority × priorityScore
  + w_dueTime × dueTimeScore
  + w_bottleneck × bottleneckProtectionScore
  + w_load × loadEfficiencyScore
  - w_travel × travelCostScore
  - w_wait × downstreamWaitRisk
```

评分只能在硬约束和授权预算之后使用，不能用高分任务突破容量、库存和时段约束。

### 4.6 休息时段与跨日

休息时段只暂停新任务启动，事件进入队列；营业时段恢复后按原发生时间和优先级重新计算。

第一版规则：

1. `12:00—13:00` 和 `18:00—18:30` 不启动新任务；
2. 已开始任务按场景参数决定是否允许完成，基线任务不跨越休息时段；
3. 休息期间产生的到货、发运和订单释放事件进入队列；
4. 下一营业时段先处理影响库存、位置和资源的事件，再生成后续工序和任务；
5. `21:45` 后不释放预计无法在 `22:00` 前完成的任务；
6. `22:00` 仍未完成的 L1、L2、L3 记录为跨日积压，不伪造为完成。

## 7. 验证方法

验证分为数据校验、守恒校验、过程校验和策略校验四层；四层都通过，结果才可用于比较。

### 7.1 数据校验

校验输入字段完整、引用有效、容量非负、节点可识别、资源能力匹配和时间窗口合法。

### 7.2 守恒校验

每个 SKU、批次、容器和位置都要满足数量守恒：

```text
期末库存 = 期初库存 + 入库完成量 - 出库完成量 ± 调整量
```

每个位置都要满足占用守恒：

```text
期末占用 = 期初占用 + 流入完成量 - 流出完成量
```

预占不能进入实际占用，任务取消时未完成预占必须释放。

### 7.3 层级回写校验

```text
L3 完成数量之和 = L2 完成数量
L2 必需节点完成数量之和 + 跳过数量 = L1 节点计划结果
L1 完成数量不超过 L1 计划数量
```

当节点被跳过时，跳过数量不计入该节点完成量；当节点阻塞时，L1 不得被标记为已完成。

### 7.4 过程校验

固定使用以下场景做回归：

| 场景 | 需要验证的结果 |
|---|---|
| 普通采购入库 | 到货签收、质检、装容器、上架按顺序生成 |
| 供应商免检入库 | 质检节点跳过且有原因，不生成质检任务 |
| 越库转运入库 | 上架节点跳过，货物进入对应出库链路 |
| 普通销售出库 | 补货、拣货、复核、打包、交接按前置关系推进 |
| 整托出库 | 拣货、复核和打包跳过，直接生成出库交接 |
| 拣选位缺货 | 先生成补货工序和任务，拣货保持等待或阻塞 |
| 出库暂存满 | 出库交接被空间约束阻塞，发运释放后恢复 |
| 休息时段到货 | 事件进入队列，下一营业时段处理 |
| 共享通道冲突 | 同一时段只允许一台叉车占用通道 |
| 营业日结束 | 未完成单据、工序和任务形成跨日积压 |

### 7.5 策略对比

策略对比必须使用相同输入、相同随机种子和相同结束条件，只替换调度策略；至少比较：

```text
idle-first
score-only
budget-reservation-score
```

比较指标按字典序输出：

1. 瓶颈通过率；
2. 完成的 L1 单据量和完成率；
3. L2 工序完成率与跳过率；
4. L3 任务完成率、阻塞率和跨日积压；
5. 库位、暂存位、通道和人员的峰值占用；
6. 平均等待时长、P95 等待时长和同步损失；
7. 资源利用率和瓶颈持续时间。

## 8. 实施顺序

实施顺序必须先稳定数据和状态，再加入策略比较，避免调度算法掩盖单据、节点和任务关系错误。

| 阶段 | 交付内容 | 通过条件 |
|---|---|---|
| 第 1 阶段 | 场景加载、输入校验、位置和库存模型 | 非法引用和容量错误能被拦截 |
| 第 2 阶段 | L1 单据、节点编排、L2 工序派生 | 需要节点生成，不需要节点跳过且留痕 |
| 第 3 阶段 | L3 任务拆分、状态迁移和数量守恒 | 任务能回写工序和单据 |
| 第 4 阶段 | 预占、事件队列、营业时段和共享通道 | 库存、位置、资源和时间约束有效 |
| 第 5 阶段 | 调度策略、评分、决策日志 | 相同输入下结果可重复 |
| 第 6 阶段 | 输出文件、瓶颈分析、策略对比 | 能解释单据卡点、资源瓶颈和空间峰值 |

第一阶段到第四阶段形成最小可运行闭环；第五阶段和第六阶段用于比较策略和支撑后续产品设计。

## 9. 需要在程序开发前确认的口径

以下事项会影响计算结果，应在写实现代码前固定；当前场景资料已给出默认值，未确认部分标记为待定。

| 事项 | 当前建议 | 未确认时的处理 |
|---|---|---|
| 入库到货与入库单的关系 | 到货事件回写 L1 入库单，再生成后续工序 | 不允许到货事件直接生成任务 |
| 质检失败 | 进入异常库存或阻塞，不进入可用库存 | 第一版可先只模拟通过和跳过 |
| 任务是否跨休息时段 | 基线不跨，休息时段暂停新任务 | 作为策略参数保留 |
| L2 合并粒度 | 同仓、同作业批次、同工序、兼容容器时合并 | 不满足条件则拆分 |
| 补货来源 | 储备箱格库位或托盘拆箱后的可用库存 | 未找到来源时任务阻塞 |
| 整托出库 | 跳过拣货、复核、打包，保留出库交接 | 以单据属性为准 |
| 单据完成口径 | 所有必需 L2 完成，跳过节点有记录，数量达成 | 不用任务数替代单据完成量 |
| 随机性 | 只用于并列决策和批量数据生成 | 默认固定 `seed` |

## 10. 方案验收标准

程序方案验收以“能否解释一张单据如何变成任务，以及任务如何改变仓内状态”为主，不以单次完成任务数量为唯一标准。

必须同时满足：

- 输入中有足够数量的入库单、出库单及明细行；
- 每张 L1 都能得到节点需要、节点跳过或节点阻塞的明确结果；
- 每个必需节点能生成可追溯的 L2 工序单据；
- 每个 L3 任务都能追溯到 L2 和 L1；
- 跳过节点不生成占位任务，且保留跳过原因；
- 库存、位置、资源和通道预占不会超过容量；
- 任务完成会回写库存、位置、资源、L2 和 L1；
- 休息时段、发运释放和营业日结束规则可复现；
- 输出能定位单据卡点、节点等待、任务阻塞和瓶颈资源；
- 相同输入、策略和随机种子可以得到相同结果。
