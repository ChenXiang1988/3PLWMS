# 多平台一致性字典对照清单

**目标读者**：产品、原型维护人。
**核心目的**：把 `humanfile/功能结构描述.md` 点名的核心命题「如何用一套软件，去服务多个平台，以及如何保证各个平台的数据一致性」拆成可判定的事，逐项对照现有数据字典与方案文档，列清哪些已有字段或状态落点、哪些没有。不排优先级，不做推断。
**前提**：本清单只做核对，不改字典、不改原型、不改 `CODEBUDDY.md`。不引用店小秘实测（账号未授权任何平台，不能作为能力依据），不写领星、聚水潭、旺店通（未调研）。

## 3. 逐项对照

### P1 平台差异配置化

已有落点：

| 实体 | 字段 key / 枚举 |
| --- | --- |
| 平台应用 | `capabilities`（订单 / 履约 / 售后 / 物流 / 面单 / 商品）、`appType`（自建应用 / 合作伙伴应用）、`authMode`（OAuth / API Key / 店铺授权）、`rateLimit`、`appVersion`、`auditStatus`（待提交 / 审核中 / 已通过 / 已驳回 / 已停用） |
| 平台订单 | `platformCode`、`orderType`（全托管 / 半托管 / 自营 / FBA / FBM / 其他）、`fulfillMode`（仓发货 / 自发货 / 平台备货）、`platformStatus`（平台原始状态）、`syncStatus`（待同步 / 已同步 / 同步失败） |
| 平台店铺 | `platformCode`、`shopType`（全托管 / 半托管 / 自营）、`region`、`sellerId` |
| 方案文档 | `platformCode + orderTypeCode` 配置矩阵的 10 项配置项：履约责任方、备货位置、发货对象、面单来源、承运商规则、发货时限与揽收时限、平台状态映射、退货归属、结算方式 |

未见落点：

- 「平台 × 订单类型配置」没有独立实体，10 项配置项只在方案文档表格里，没有字段 key。
- 平台状态映射表没有实体。`platformStatus` 存平台原文、`orderStatus` 存聚合状态，两者之间的映射规则没有落点。
- 平台清单是多个字典里的枚举硬编码（速卖通 / Amazon / Temu / Shopee / Lazada / 美客多 / 其他），没有平台主档实体。
- 适配器契约与能力矩阵的版本化发布没有实体，只有 `appVersion` 一个字符串。

判定：B（字典无落点），其中能力矩阵的部分内容属于 C。

### P2 凭证集中与卖家授权

已有落点：

| 实体 | 字段 key / 枚举 |
| --- | --- |
| 平台应用 | `appKeyMasked`（脱敏 App Key）、`callbackUrl`、`authMode`；约定「App Secret 不落页面、不进演示数据」 |
| 店铺授权 | `authNo`、`authStatus`（已授权 / 即将过期 / 已过期 / 已撤销 / 授权失败）、`authScope`、`expireTime`、授权日志 `operator` / `action` / `actionTime` / `actionDetail`；约定「重新授权追加不覆盖」 |
| 平台店铺 | `authStatus` 六值（多一个待授权）、`authNo`、`authScope`、`authTime`、`expireTime`、`lastSyncTime`、`failReason` |

口径冲突（不是加字段能解决的）：

- `平台应用.md` 的 `callbackUrl` 写「客户侧网关公网地址」，`需求问答.md` Q10-1 结论是「部署级应用 + 客户侧网关，订单数据不过厂商」。这与「服务端统一持有应用凭证」相反。
- `平台应用.md` 第 44 行「不出现运营后台类 SaaS 术语」、`ERP模块.md` 第 31 行「不写商业化字段：不建价格、周期、商业化分层字段」、`货主开通.md` 第 5 行「不使用商业化账号分层用语」，与卖家自助注册 / 试用 / 订阅相反。
- `子账号.md` 的 `accountDomain` 只有 `erp` / `network` 两值，是产品域，不是租户。

未见落点：

- 49 份字典没有租户实体，没有 `tenantId`；归属维度一律是 `ownerCode` / `ownerName`，多处写「列表按登录货主限定，不提供货主筛选」。
- `货主开通.md` 是运营中台开通货主的记录（`signStatus`、`erpStatus` 三值、`version`、`expireDate`、`modules`），不是卖家自助注册。
- `ERP服务费账单.md` 有 `accountCode`（注册账号，未签约也能出账）、`chargeItem`（账号数 / 订单量 / 功能模块）、`chargeQty`、`unitPrice`、`billStatus` 五值，是最接近订阅计费的实体；但口径写「按当期实际用量结算」「不引入按周期预收的说法」，是后付费用量账单，不是订阅套餐。

判定：A（口径冲突）+ B（缺实体 / 字段）。

### P3 拉取与回传

已有落点：

| 实体 | 字段 key / 枚举 |
| --- | --- |
| 同步任务 | `syncType`（拉单 / 回传 / 售后）、`triggerType`（定时 / 手动 / 重试）、`windowStart` / `windowEnd`、`taskStatus`（待执行 / 执行中 / 成功 / 部分失败 / 失败）、`successCount` / `failCount` / `retryCount` / `failReason` |
| 平台订单 | `syncStatus`、`syncTime`、`failReason` |
| 平台售后单 | `syncStatus`（回传状态）、`failReason` |
| 平台应用 | `rateLimit`（如「100 次/分钟」，按平台声明） |
| 方案文档 | 每店一条队列、平台级限流、全局并发上限、店间公平调度、平台级熔断、失败重试与死信重放；拉单只写订单中心不自动下发，已下发时拦截转人工 |

未见落点：

- 队列、租户配额、租户间公平调度、熔断状态、死信重放都没有字典落点。`同步任务.md` 第 8 行明确写「每店队列、平台限流、全局并发上限由产品侧实现，原型只展示」，属于 C，字典不承担。
- `rateLimit` 是展示用字符串，不是可执行配额模型。
- 方案只写了「店与店公平」，没有租户级配额与租户间公平调度的字段或规则。

判定：C 为主，B 为配额模型。

### P4 数据一致性

已有落点：

| 实体 | 字段 key / 枚举 |
| --- | --- |
| 同步任务 | `cursor`、`pageCount`、`lastSuccessTime`、`nextRetryTime`；第 3 节关系写明幂等键 `shopCode + platformOrderNo`、`platformAfterSaleNo`、`waybillNo` |
| 平台订单 | `platformOrderNo`（同平台同店铺内唯一）、`fulfillmentCount`、`planNo` 只存首张主履约单号、`refundStatus` |
| 差异异常单 | `exceptionType`、`sourceDomain`（订单 / 平台同步 / 履约 / 售后 / 账单 / 仓储）、`sla`、`diffQty`、`exceptionStatus`（待处理 / 处理中 / 已处理 / 已驳回） |
| 方案文档 | 对账类型 5 类（订单同步 / 履约 / 运单 / 账单 / 售后）、差异类型 5 类（单号缺失 / 状态不一致 / 数量不一致 / 金额不一致 / 重复单）、四单对账口径「平台单 ↔ ERP 订单 ↔ 履约/运单 ↔ 账单/售后」 |

未见落点：

- 「对账差异」没有独立字典实体。`ERP履约控制台优化方案.md` 第 82 行明确写「不新建对账主表，页面是现有单据的差异视图」——这是有意的设计决策，不是遗漏。
- 平台状态一致性校验规则、重复单识别规则没有落点。
- 幂等键是文字约定，没有字段定义或唯一约束。
- `差异异常单.md` 的 `exceptionType` 取值是收货差异 / 盘点差异 / 破损丢失 / 批次不符 / 跨货主串货 / 费用对账，与方案里那 5 类平台侧差异类型不是同一套枚举。

判定：B 部分 + 有意不建主表 + 枚举待对齐。

## 4. 缺口汇总

| 类型 | 含义 | 条目 |
| --- | --- | --- |
| A 口径冲突 | 要改口径，不是加字段 | ① 应用凭证归客户侧网关 vs 服务端统一持有；② 三处「不写商业化 / SaaS 术语」约束 vs 卖家自助订阅；③ 归属维度是货主、账号域是产品域 vs 租户；④ 审计筛选按货主 vs 按租户 |
| B 字典无落点 | 需要实体或字段 | ① 租户实体与 `tenantId`；② 平台 × 订单类型配置；③ 平台状态映射表；④ 平台主档；⑤ 适配器 / 能力矩阵版本化；⑥ 租户配额与公平调度；⑦ 同步健康；⑧ 全局审计；⑨ 幂等键字段化；⑩ 平台侧差异类型与《差异异常单》枚举对齐 |
| C 产品侧实现，字典不承担 | 字典明确不承载 | ① 每店队列、平台限流、全局并发、熔断、死信重放（`同步任务.md` 第 8 行）；② 对账主表（`ERP履约控制台优化方案.md` 第 82 行明确不建） |

另有一处口径待收窄：`平台应用.md` 的 `callbackUrl` 指向客户侧网关，若凭证改由服务端持有，这个字段的取值口径和是否保留都要重定。

## 5. 证据边界

- 49 份字典状态全部为「草案」；原型是静态 JSON 加 `sessionStorage`，不发起网络请求；方案文档明确不实现真实平台接口、OAuth、队列、限流与资金对账。本清单的「已有落点」指设计口径有字段或枚举，不代表系统已实现。
- 「未见落点」指本次核对的文件范围内没有找到，不推断产品实际能力。
- 37 份未逐字核对的字典不纳入结论；`操作日志.md` 只依据 `index.md` 说明行。
- 客群痛点优先级未做客户验证，本清单不排功能顺序，也不写「超越」结论。

## 6. 落地前置

1. 本清单只登记自身，不改字典、不改原型、不改 `CODEBUDDY.md`。
2. 改字典前按 `docs/数据字典/index.md` 使用规则；改任一端原型前按「跨端联动确认」出评估清单。
3. 字段与文案先改字典与 `glossary.md`，再改页面。
4. 提交前跑 `node docs/check.mjs` 与 `node docs/数据字典/check.mjs`，两者零错误。
