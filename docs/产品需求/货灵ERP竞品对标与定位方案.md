# 货灵ERP 竞品对标与定位方案

**目标读者**：产品、原型维护人。
**核心目的**：以店小秘、领星为对照，定下货灵ERP 的差异化定位、核心设计方向与功能取舍，给出后续页面增量与商业化建议。
**前提**：对标主体是货灵ERP 端，不是整个产品群。本文只定定位与架构取舍，不改原型、不改数据字典；落到页面的动作另走「跨端联动确认」。

> 实施状态（2026-11-09）：商品中枢已落 4 页（SPU 列表、平台 Listing、刊登任务、采集箱），商品详情与商品配对并入 SPU 列表行抽屉；店铺报表、订单利润报表已落；订单 360 补利润字段。货灵ERP 由 38 页增至 44 页，与本文件 §6.4 的「5 页」差一页，差在商品详情不建独立页。

## 3. 定价结构分析

两家都把「功能」几乎全开，用「用量」分层。这不是慷慨，是把获客成本前置：免费版用来承接铺货卖家的第一年，付费点卡在规模增长上。差别在卡什么：

- **店小秘卡店铺数**。铺货卖家的店铺数是线性增长的，卡店铺等于卡铺货规模。代价是单店精品卖家觉得不值——一个店也要买 VIP1。
- **领星卡订单量**。低单量高客单的精品卖家能长期白用；一旦单量上来，费用跟着涨，且需要询价，价格不透明本身就是筛选器——它筛掉了不会算账的小卖家。

两条锚点对应两种增长模型：店小秘靠店铺数扩张收费，领星靠单量扩张收费。从公开计费口径看，**两家都没有把「履约」作为计费单位**：店小秘的仓储在其自营仓作业体系内，领星的仓储走海外仓备货，都不构成订阅档位的计价维度。

这给货灵留了一个空位：货灵ERP 与仓配同源，委托单是可以计量的。把「ERP 订阅」和「仓储服务费」分开计价，既不吓退只用 ERP 的卖家，也让用了仓的卖家在同一条链上结算。

## 4. 差异化定位

### 4.1 三家的位置

按两个轴看：横轴是多平台广度与铺货效率，纵轴是订单之后的能力深度（履约、财务、供应链）。

| | 平台与铺货广度窄 | 平台与铺货广度宽 |
| --- | --- | --- |
| **订单之后的能力深** | 领星：亚马逊精品，财务与供应链深 | **货灵ERP：多平台 + 履约闭环 + 订单级财务** |
| **订单之后的能力浅** | — | 店小秘：铺货效率高，履约停在打单流水线 |

两个维度都要，不等于把两家的功能表加起来。货灵要同时具备铺货广度与履约闭环，靠的是一个共用地基：**商品中枢**。一个 SPU 管住它在所有平台的 listing、库存与价格，铺货和履约才有同一份数据可用。否则就是两套商品、两套库存，铺货做快了履约就散，履约做细了铺货就慢。

### 4.2 定位陈述

> **面向多渠道卖家的商品与履约中枢：一个商品管住所有平台的 listing、库存与订单；铺货靠它放量，履约靠它收口。**

拆开是三句话：

1. **商品是地基，不是附属。** SPU → 变体 → 平台 Listing → 仓储 SKU 四层。一个商品在十个平台的价格、库存、上下架状态，在中心改一次，不是去十个后台各改一次。
2. **两条路径共用一条链。** 铺货路径是「采集进来 → 批量推到 N 个平台」；履约路径是「平台订单回来 → 渠道单 → 履约单 → 执行单」。两条路径吃的是同一份商品与库存数据。
3. **货源与仓配在同一套数据里。** 铺货卖家缺货时进商城找货源、走一件代发，货到了能进仓。这是店小秘和领星结构上做不到的，因为它们没有货源和仓网。

### 4.3 四个支点的边界

| 支点 | 能做 | 不能吹 |
| --- | --- | --- |
| 商品中枢 | 一个 SPU 管多平台 listing、批量改价改库存、批量上下架 | 不等于采集能力比店小秘强；采集来源与成功率是工程活，不是模型优势 |
| 履约闭环 | 决策可追溯、异常可归属、四单对账 | 不等于仓内作业强，仓内是货灵WMS 的事 |
| 货源直连 | 商城一件代发、工厂货源、代发采购 | 不等于货源自营，货源规模取决于招商，不是产品能力 |
| 仓配同源 | 委托单据直连仓网、服务费同链结算 | 只是 ERP 的一项能力，不是「我们和店小秘不一样」的全部理由 |

## 5. 核心设计方向

### 5.1 原则一：商品先立中枢，再谈多平台

现有商品主档是仓储视角的 SKU：`skuCode`、条码、箱规、效期、库容。它回答「这个货怎么存、怎么拣」，不回答「这个商品在亚马逊叫什么标题、有几张主图、在 Shopee 卖多少钱」。铺货加强的真实成本不在页面，在这里：要新增一层电商商品模型。

| 层 | 回答什么 | 与现有资产的关系 |
| --- | --- | --- |
| SPU | 这是什么商品：标题、描述、类目、属性、主图 | 新增 |
| 变体 | 颜色/尺码/规格，一个变体对应一个可售单元 | 新增，可关联仓储 SKU |
| 平台 Listing | 这个商品在某平台某店铺的售卖页：平台商品 ID、平台 SKU、价格、库存、状态 | 新增，挂在平台店铺下 |
| 仓储 SKU | 这个货怎么存、怎么拣、怎么算效期 | 已有 `商品主档`，语义不改 |

关键设计：**SPU 与仓储 SKU 的关联可为空**。铺货卖家一件代发，商品不进仓，SPU 直接连货源与供应商，不强迫建仓储 SKU；货到仓再补配对。这是铺货与履约能在同一套模型里共存的唯一办法。

**边界**：商品中枢不等于采集能力。采集来源（1688、链接、插件）、平台类目映射、刊登成功率是适配器与工程问题，本文只定模型。

### 5.2 原则二：一套订单模型，不为平台建页面

店小秘的反面教材是明摆着的：Temu 全托管/半托管/本土、TikTok 全托管/美国本土、速卖通 POP/半托管/全托管、Lazada 全托管、Shopee 全球/本土/全托管/SIP，每个组合一条授权入口、一篇刊登文档、一套订单处理流程。用户要记 20 多条路径。

货灵的做法是把平台差异压进两个维度：`platformCode` × `orderTypeCode`，由配置矩阵决定履约责任、备货位置、面单来源、时效与状态映射。页面只有一套，页签不按平台分。

**边界**：配置矩阵不是万能。平台 API 的字段差异、状态机差异仍要适配器承接，适配器按版本发布，不到客户现场改代码。

### 5.3 原则三：履约可追溯，异常有归属

店小秘有审单规则，但规则执行后只「打上标记/备注」，看不到为什么这单走了这个仓、这个承运商。领星偏数据，履约过程本身不落决策记录。

货灵的对应物是订单 360 与履约决策记录：一张订单聚合渠道、履约、仓单、运单、售后、账单，决策表记录方式、仓、承运商、承诺时间与拆分原因。异常不是订单列表里的一个筛选条件，是独立队列，且能追到是哪一步出的问题。

### 5.4 原则四：货源与仓配是链路，不是模块

商城店铺、仓储委托在导航里是两段，但在数据上是一条链：商品配对 → 代发采购单 → 入库计划单 → 出库计划单 → 执行单 → 服务费账单。链断了，货灵就退化成「又一个店小秘」。

### 5.5 原则 → 结构 → 字段 映射

| 原则 | 结构约束 | 字段约束（设计期清单，真值见数据字典） |
| --- | --- | --- |
| 商品中枢 | 商品段 5 页；Listing 与配对放 SPU 详情页签，不单开页 | SPU 主键、变体、平台 Listing（平台商品 ID + 平台 SKU）、SPU↔仓储 SKU 可空关联、价格与库存的推送状态 |
| 一套订单模型 | 订单段不超过 4 页；页签按状态分，不按平台分 | 三层单据主键与关联；`platformCode`、`orderTypeCode`、幂等键 `shopCode + platformOrderNo` |
| 履约可追溯 | 订单 360 做成抽屉，不新开页面；异常单独成段 | 决策记录：决策类型、仓、承运商、承诺时间、拆分原因、决策人、时间；异常：类型、来源单、归属环节、责任方 |
| 货源与仓配是链路 | 商城店铺与仓储委托两段各不超过 5 页 | 委托单号在采购单、入/出库计划单、执行单、账单五处可反查 |
| 平台差异配置化 | 平台接入段只做授权与同步，不做平台专属页 | 授权 6 态；同步任务 5 态；适配器版本号 |

## 6. 功能架构

### 6.1 五层

```
商品层   SPU ──→ 变体 ──→ 平台 Listing（平台 × 店铺）
                      └──→ 仓储 SKU（配对，可为空）
            ↓
接入层   平台适配器（授权 / 刊登 / 拉单 / 回传）  商城货源  仓网委托
            ↓
主干层   渠道单 ──→ 履约单 ──→ 执行单
            ↓
能力层   库存 ATP  售后  代发采购  订单利润  头程
            ↓
闭环层   异常队列  四单对账  委托单据中心  服务费账单
            ↓
数据层   固定报表（周转 / 履约时效 / 费用构成 / 订单利润）
```

商品层是新增的，其余四层沿用现有方案。商品层不放在接入层之后，是因为它同时服务两条路径：铺货从它出去（刊登），履约从它回来（订单关联库存）。

### 6.2 能力取舍

判断标准只有一条：不做这个，第 4.2 节的定位成不成立。

| 能力域 | 取舍 | 理由 | 分期 |
| --- | --- | --- | --- |
| 商品中枢（SPU / 变体 / 平台 Listing） | **做** | 铺货与履约共用的地基；不做则两条路径各建一套商品，必然分叉 | P0 |
| 商品配对（平台 SKU ↔ 仓储 SKU） | **做** | 拉回来的单要能关联库存；放在 SPU 详情里，不单开页 | P0 |
| 采集（1688 / 链接）与批量刊登 | **做** | 铺货的入口与出口。只做这两条来源与按平台的发布适配，不做全渠道采集与图片处理 | P0–P1 |
| 订单利润（订单级） | **做** | 卖家选 ERP 的硬指标。口径见 6.3，只算订单级财务事实，不做分摊 | P0 |
| 代发采购单 | **补强** | 已有页面，需与商城货源打通 | P0 |
| 头程物流单 | **做（轻）** | 与仓配同源是差异化；只做单据与轨迹，不做比价 | P1 |
| 客服消息聚合（站内信 / 邮件） | **做（聚合）** | 只聚合与订单相关的消息并跳转平台回复，不做智能客服与自动催付 | P1 |
| 广告管理 | **不做** | 领星的深度靠亚马逊广告 API 长期投入换来，不是页面问题 | 不做 |
| BI 自定义报表 | **不做** | 固定报表覆盖 90% 场景；自定义是专业分析工具的事 | 不做 |
| 平台仓 / FBA | **保留** | 已有平台备货单，够用 | — |

取舍后的页面增量：38 页 → 约 45 页。两家的功能表加起来是 80+ 页，差距不在做少了什么，在商品层复用了同一份数据。

### 6.3 订单利润的口径

只算订单级财务事实，不做分摊。

| 项 | 取值 | 来源 |
| --- | --- | --- |
| 商品售价 | 订单明细行金额 | 平台订单 |
| 买家实付运费 | 订单运费 | 平台订单 |
| 平台佣金与手续费 | 平台费率 × 订单金额，或平台回传的实际扣费 | 平台结算 / 费率配置 |
| 物流费 | 实际面单费用 | 运单 |
| 采购成本 | 代发采购单单价 × 数量，或仓储 SKU 成本价 | 采购单 / 商品主档 |
| 退款 | 已退款金额 | 售后单 |
| **毛利** | 收入 − 上述成本 | 计算 |

**不做**：广告费分摊、头程运费分摊、包材分摊、仓储服务费分摊。这些的分摊维度（按订单、按 SKU、按重量、按期）是运营与财务口径问题，不同卖家答案不同；强行分摊会让订单利润变成一个没人信的估算值。先给能对得上账的订单级事实，分摊留给后续独立的成本核算模块。

## 7. 商业化建议

### 7.1 三档结构

| 档位 | 店铺数 | 月订单量 | 3PL 委托 | 定位 |
| --- | --- | --- | --- | --- |
| 免费版 | 1 | 500 | **含，月 20 单以内** | 仓配是钩子：先用 ERP 管店，货要进仓时链路已经通了 |
| 标准版 | 5 | 5,000 | 按单计费 | 主力档，对标店小秘 VIP1（2016 元/年） |
| 专业版 | 20 | 不限 | 按单计费，含对账与异常 | 对标店小秘 VIP2–VIP3、领星包年版下限 |

**免费版含委托，但必须限额。** 仓配是成本中心，免费用户无限委托等于用软件补贴仓储。20 单/月够跑通「报备商品 → 入库计划 → 出库计划 → 账单」整条链，够验证价值，不够当免费仓用。限额按委托单量还是按库存容积分，需要与仓网侧的计费口径一起定，见第 8 节。

**锚点选择**：店铺数为主、订单量为辅。理由：货灵定位多渠道卖家，店铺数是他们的核心变量；纯按单量会把低单量多店铺的铺货卖家挡在门外，而那正是免费版要承接的人。

**价格带**：标准版落在 2000–4000 元/年，专业版 8000–15000 元/年。低于店小秘同档、显著低于领星，用「商品中枢 + 履约闭环 + 货源」补差价。具体数字需与成本、渠道政策一起定，本文只给区间。

### 7.2 与仓储服务费的关系

ERP 订阅与仓储服务费**分账**：订阅是软件费，按年预付；仓储是按委托单量的服务费，走月度账单与对账。两者不在同一张账单上，避免卖家把「用了仓」和「买了软件」绑死，也避免仓配亏损拖累软件定价。

## 9. 缺项与保鲜期

- **商品模型缺 SPU 与 Listing**。现有 `商品主档` 是仓储视角的 SKU，`docs/数据字典/` 中没有 SPU、变体、平台 Listing 三类实体。第 5.1 节的四层模型是设计期提案，落地前需先建三份字典并评审；字典未定之前，6.4 的五个页面不能开工。
- **领星未登录**。功能深度、字段、状态机、真实交互全部未验证，本文对领星的判断只到「官方怎么描述 + 第三方怎么说」。要补到店小秘那份文档的颗粒度，需要账号实见，见 `店小秘与领星ERP菜单结构.md` 的待复核项。
- **定价为公开口径**。领星包年档位不公开，0.04 元/单与 1 万–20 万区间来自第三方（C），实际成交价以销售报价为准；店小秘年费为官方博客口径（B），是否含折扣未说明。
- **客群规模为厂商口径**。180 万、70 万、市占率第一均为官方或引用第三方，未独立核验。
- **保鲜期**：竞品定价与菜单每季度复核一次，产品大改版后立即复核，并在 `docs/log.md` 留痕。
