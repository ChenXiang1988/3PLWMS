# 货灵ERP 交付形态方案

**目标读者**：产品、原型维护人。
**核心目的**：定下货灵ERP 作为单独售卖软件交付给跨境电商卖家的形态，以及它与货源商城、中台、仓配侧的关系。
**前提**：口径来自 `humanfile/产品群能力设计思路.md`、`humanfile/功能结构描述.md`（人类书写区，只读）与 2026-11-08 用户口径。本项目当前交付物是五端自包含 HTML 原型，没有后端、数据库与真实前端工程；本文只定产品交付形态，不改原型、不改数据字典、不改 `CODEBUDDY.md`。

## 2. 客群与两个入口

- **铺货卖家**：在各平台开店但没有货，通过货源商城找货源、一件代发或批量采购。对应 `humanfile/功能结构描述.md` 的「卖家虽然在各个平台开店了，但是没有货，然后要通过这个平台去找货源，然后去做代发」。
- **直做 POP 卖家**：自己在平台开 POP 店、自己备货发货。对应同一份文件里「外部平台的刊登、订单同步」。

两类卖家共同要的是：多平台店铺接入、刊登、订单拉取与同步、打单发货。铺货卖家多一条商城货源与代发链路；POP 卖家多一条自有库存与发货。客群画像来自 humanfile 与用户口径，**痛点优先级未做客户验证**，本文不据此重排功能顺序。

## 3. 产品群三套交付

| 交付 | 面向 | 内容 | 售卖 / 部署 | 与货灵ERP 关系 |
| --- | --- | --- | --- | --- |
| 货灵ERP | 跨境电商卖家 | 平台店铺接入、刊登、订单同步与处理、发货、售后、库存查询、报表、账号权限 | 单独售卖的软件，多卖家 | 产品群获客入口 |
| 货源商城 + 中台运营 | 平台运营方、货源工厂、卖家的店铺后台 | 货源商城（一件代发 / 批量采购）、商城管理、仓网管理、订单分发与跟踪、SLA、物流服务商接入、报表可视化 | 平台方运营 | 铺货卖家的货源入口；货主端即商城店铺后台 |
| 仓配侧 | 有货源的工厂、仓网与单仓运营方 | 仓储、国内快递、头程、关务；仓网调度；单仓作业（WMS+WES+WCS）；PDA 作业 | 另一套交付 | 卖家不直接购买；ERP 通过委托单据接入 |

「这是一套产品，不是一个产品」讲的是生态闭环：ERP 获客 → 卖家规模 → 引入工厂与货源 → 商城及仓配服务跟上。它不等于同一套软件里装五个端，也不等于五端共用一套租户模型。

## 5. 核心命题：一套软件服务多个平台 + 数据一致性

这是 humanfile 点名的最关键一条，拆成五件可判定的事：

1. **平台差异不按平台建页面**：按 `platformCode + orderTypeCode` 配置矩阵表达履约责任、备货位置、面单来源、时效与状态映射；适配器契约与能力矩阵决定页面显隐；平台 API 变更走适配器版本发布，不到客户现场改代码。
2. **应用凭证集中**：服务端统一持有平台应用，App Secret 不落页面；租户侧只做店铺授权，授权 6 态（待授权 / 已授权 / 即将过期 / 已过期 / 已撤销 / 授权失败）。
3. **拉取与回传**：每店一条队列、平台级限流、全局并发上限；拉单只写订单中心不自动下发，已下发时拦截转人工；售后同步与逆向入库按 `bizType` 处理。
4. **一致性**：幂等键 `shopCode + platformOrderNo` / `platformAfterSaleNo` / `waybillNo`；同步任务 5 态（待执行 / 执行中 / 成功 / 部分失败 / 失败），带游标、页数、重试次数、下次重试时间与失败原因；部分失败、重试耗尽、告警与待办可查。
5. **可追溯**：同步健康只读、全局审计跨租户只读且动作留痕不可删除；运营方代维只开只读摘要。

以上均为方案文档与数据字典的**设计口径，状态为草案**。原型明确不实现真实平台接口、OAuth、队列、限流与资金对账，同步任务与对账只是展示视图，不能当作已实现能力。
