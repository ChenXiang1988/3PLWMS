# 单仓端三模块设计方案（参照 proto-next）

**目标读者**：产品、原型维护人、研发。
**核心目的**：参照 `proto-next` PC 原型的「仓库单据 / 单仓配置 / 任务中心」三段，定单仓端的功能范围、页面组成、数据流转与界面结构，作为原型落地依据。
**前提**：独立部署、单一运营主体；货主是业务实体，不是租户。端名与端数以 `prototypes/shared/modules.json` 的 `apps[]` 为准，仍是货主端、仓网管理端、单仓端、商城端四个端；`humanfile/` 是只读草稿。字段真值见 `docs/数据字典/`，文案见 `.codebuddy/skills/3pl-wms-proto/references/glossary.md`，装配见 `prototypes/shared/modules.json`。

**本文使用规则**：本文只定设计口径，不另起页面清单。逐页映射复用 [原型同步方案.md](原型同步方案.md) 第 3、4 节，分批复用 [端定位补齐方案.md](端定位补齐方案.md) 第 3.2 节与 A~E 批，功能范围以 [三端核心功能清单.md](三端核心功能清单.md) 的单仓端条目为准。页面名、列名、状态中文名一律先按 `glossary.md` 第 6 节登记；本文未登记的名称均为拟名，登记前不得写进页面。

## 1. 参照对象与一致性基线

`proto-next` 的 PC 端把 8 个一级分组、59 页全渲染进一份 `dist/pc.html`，靠 hash 切页。「仓储库存」下三个二级段由 `pc/src/menu.mjs` 的 `SCOPED_SECTIONS = {'conf','docs','task'}` 标为按仓切：页头「仓库」下拉只在这三段生效，`shell/warehouse-scope.js` 过滤带 `[data-wh]` 的行；判据是「这行数据属不属于某一座具体的仓」。三段共用 `shared/data/` 的 47 份 JSON 与 `shared/doc-status.mjs` 状态机。

| 段 key | 名称 | 页数 | 定位 |
| --- | --- | --- | --- |
| `conf` | 单仓配置 | 9 | 本仓作业资源台账与作业规则，决定「谁能做、在哪做、按什么顺序做」 |
| `docs` | 仓库单据 | 8 | 本仓 L1 单据主档、承诺交付与工序卡点 |
| `task` | 任务中心 | 7 | L3 作业任务台账、负载看板与派工执行反馈 |

保持一致的三个层次：

| 层次 | 一致的内容 | 本项目落点 |
| --- | --- | --- |
| 能力域 | 单据受理与跟踪、本仓配置、任务派工三段分立，互不替代 | 第 2 节 |
| 页面职责 | 一页一事；列表=状态页签＋筛选＋工具条＋表格，看板=汇总与卡点，扫码=单据/任务上下文 | 第 6 节 |
| 数据链 | L1 计划单 → L2 工序单（收货 / 上架 / 拣货 / 复核 / 交接…）→ L3 任务 → 库存账；工序单由单仓生成，波次是拣货的排程容器；状态由任务聚合 | 第 4 节 |

不一致的部分集中在装配形态、业务口径与技术实现，逐条列在第 8 节，不改动上述业务结构。

## 2. 模块划分

**模块＝源组织单元，端＝交付单元**（`references/registry.md` 第 1 节）。三段在外部是菜单段，在本项目是**能力域**，不新建三个同名模块：页面仍放在既有模块目录，由注册表 `pages[].app = "warehouse-app"` 决定进单仓端产物，`deployed` 决定整块是否装配。端 id 统一带 `-app` 后缀（`owner-app` / `network-app` / `warehouse-app` / `mall-app`），不与模块 ID 同名。

| 能力域 | 承载模块 | 边界 |
| --- | --- | --- |
| 仓库单据 | `inbound`、`outbound`、`warehouse`，聚合视图归 `task` | 本仓入库通知单、出库订单、移库/补货/盘点/上架单的受理、执行跟踪、差异与逆向闭环；不做采购单、电商订单、结算，跨仓单据归仓网管理端 |
| 单仓配置 | `resource`，库区库位归 `warehouse`，账实参数归 `inventory` | 本仓容器、设备、执行单元、班组、人员、排班台账与策略、工序编排、派工规则；档案主档与仓库级配置由仓网管理端建档下发，单仓端只做本仓实例、绑定、启停与排班 |
| 任务中心 | `task`（聚合视图）＋ `inbound` / `outbound` / `warehouse`（各链任务源） | L3 任务的聚合、派工、执行反馈与负载看板；`task` 只作视图，不持有业务源、不复制其它模块的任务数据 |

三段之外，`inventory` 的本仓明细（仓位库存、批次效期、日清检查、初始库存、库存调整任务、库存快照）是单仓端的账实层，作为数据链的终点与库存真相，不并入三段。按 [端定位补齐方案.md](端定位补齐方案.md) 第 3.2 节，任务派工层／单据执行层／账实层／设备执行层是功能分层描述，不是四套页面清单。

**侧栏呈现**：按 `references/shells/admin.md` 第 3 节，侧栏按模块分组、条目文案取 `pages[].name`，页头页签按模块成组只列本端页面。三段目前只用于功能划分与验收分组，不改写侧栏结构；若要让侧栏按三段呈现，需要改 `shared/ui.mjs` 的外壳分组逻辑，属共享层改动，须走规范第 6 节并四端全量重建，列为第 9 节待确认项。

**现状基线**：2026-11-06 单仓端产物已含 33 页——本仓商品查询与批次效期 2 页、任务中心 3 页（作业任务、作业看板、单据总览）、入库 5 页（入库计划单、入库计划单详情、收货单、工序单详情、上架单）、出库 5 页（出库计划单、拣货单、复核单、交接单、波次计划）、仓储 4 页（库区库位、移库任务、盘点任务、补货任务）、库存本仓 5 页（仓位库存、日清检查、初始库存、库存调整任务、库存快照）、作业资源 9 页（容器管理、设备、执行单元、班组、人员、排班、策略管理、单据工序编排、任务中心策略）。L1 是推送来的入库与出库计划单，L2 是单仓生成的工序单（收货单、上架单、拣货单、复核单、交接单），L3 任务派给人员或设备，工序单详情可下钻到任务。收货验收、拣货作业、盘点作业三个扫码屏归 `pda-app`（PDA 作业端 14 页），单仓端不渲染手机屏。14 个模块全部参与装配，仍为预留的只有 `system` 账号管理与角色权限 2 页。

## 3. 核心功能范围与页面组成

### 3.1 仓库单据

功能范围：单据受理与状态跟踪、明细与实收汇总、工序卡点、差异与异常登记、取消与逆向闭环、外部下发单据只读查看。单据一律带货主上下文，收货、拣货、复核、盘点扫码按本单货主限定商品集合。

| 页（模块/页 key） | 页面名 | 类型 | 职责 |
| --- | --- | --- | --- |
| `task/doc-overview` | 单据总览（拟名） | report | 本仓单据按承诺交付、卡在哪道工序、闭环是否走完 |
| `inbound/asn-list` | 入库通知单 | list | 到货单据台账，状态页签、货主筛选、数量与差异进度 |
| `inbound/asn-detail` | 入库通知单详情 | detail | 基础信息、明细行、实收汇总、任务四段 |
| `inbound/receiving-scan` | 收货验收 | scan | 按通知单扫码收货，采集批次、生产日期、实收与拒收 |
| `inbound/putaway-task` | 上架任务 | list | 上架单与上架作业任务合页，目标库位与作业进度 |
| `outbound/so-list` | 出库订单 | list | 出库单据台账，明细、包裹、物流与任务段落 |

| `staff-list` | 人员 | list | 岗位、可做工序、作业资质、班次与绑定单元 |

| 页（模块/页 key） | 页面名 | 类型 | 职责 |
| --- | --- | --- | --- |
| `task/task-list` | 作业任务 | list | 跨链任务聚合，任务类型/状态/货主/执行人/计划与已做数量 |
| `task/task-report` | 作业看板 | report | 在办合计、异常与超期、工序节点负载、窗口告警 |
| `inbound/putaway-task` | 上架任务 | list | 入库链任务源与批量确认、批量异常登记 |
| `outbound/picking-scan` | 拣货作业 | scan | 出库链任务执行 |
| `outbound/handover-list` | 发货交接 | list | 发货任务与批量发货 |

| `warehouse/count-task` | 盘点任务 | list | 库内链盘点任务源与差异复核 |

外部「复核作业任务」是整段嵌入的空态页，无字段与交互定义，按 [原型同步方案.md](原型同步方案.md) 第 2 节不纳入。

## 4. 数据流转

### 4.1 三层数据链

与 `proto-next` 一致的主链：**L1 计划单 → L2 工序单 → L3 任务 → 库存账**。计划单由货主建、仓网端确认后推送进仓，原单不改编号；工序单由单仓基于计划单生成，一道工序一张，分组依据按工序不同（收货按到货批次、上架按目标库区、拣货按波次）；波次是拣货的排程容器，不是工序单。配置链从旁决定走哪些工序与怎么派工。

波次不是「把订单合并」，是作业时段的产能切片：一个波次 = 一个时间窗口 + 该窗口能消化的作业量上限（订单数、明细行数或件数）。订单是排进波次，排得进的前提是该波次还有余量；容量由当班可用执行单元的处理能力与班组出勤人数派生，超限则拆波或顺延。

| 关联 | 外部字段 | 本项目落地 |
| --- | --- | --- |
| 单据 → 编排 | `flowRef.flowId` / `version` → `task-flows` | 单据行带 `sourceDocNo`，编排与工步落在 `resource/data/*.json` |
| 单据 → 工序/波次 | `waveNo` / `arrivalWindowNo` ↔ `batchNo`、`processOrderNo` | `wave-list` 的波次号、任务行的 `sourceDocNo` |
| 任务 → 单据明细行 | `taskId × docNo × lineNo × allocQty` | 任务页保留「来源单据号、商品编码、计划数量、已做数量」，由页面派生列算进度 |
| 任务 → 库位/容器/执行单元 | `targetLocation` / `containerCode` / `execUnitLabel` / `unitId` | 字段取 `库区库位.md`、`容器档案.md`、`执行单元档案.md`；容器占用由 `bizNo` 指向单据，作业完成释放 |
| 任务 → 策略 | `matchedStrategy` | 策略页的编码/名称与任务行的命中策略字段对应 |
| 库存账 | `inventory-stock` / `inventory-flows` | `inventory` 本仓明细与库存台账，是任务完成后的账实终点 |

数据落地方式：一页一个 `data/<页key>.json`，行字段小写驼峰、与 `columns[].key` 同名；货主、商品、仓库、批次等外键取 `shared/data/` 共享主档，构建期做一致性断言；派生列（进度、剩余天数、差异）写成页面内纯函数，不往 JSON 加展示字段。**不搬** `page-defs.json`（3.8 MB）、`bins.json`（34.78 MB）、`doc-status.mjs` 与 `verify-*.mjs` 派生脚本，也不整库复制演示数据。

### 4.2 状态流转与聚合

状态中文名与色型逐字取 `glossary.md` 第 3 节：单据状态 `pending` 待处理 / `doing` 进行中 / `exception` 异常待处理 / `completed` 已完成 / `cancelled` 已取消；作业状态 `wait` 待作业 / `busy` 作业中 / `blocked` 异常 / `done` 已完成 / `closed` 已取消。`StatusTag` 只用 `disabled` / `enabled` / `info` / `pending` / `rejected` 五种 tone。

保留外部的三条聚合规则，用演示数据与派生列表达，不做构建期状态机：

1. **工序单据状态 = 其下任务状态聚合**：任务全 `done` 才已完成，出现 `blocked` 即异常待处理。
2. **出库单据状态 = 任务聚合**：拣货、复核、交接任务全部完成才置已完成；取消请求未闭环停在「进行中」并展示返仓中。
3. **入库单据状态 = 数量口径**：按 `qtyExpected` / `qtyReceived` / 到货次数派生，与任务状态无关；差异输出短收、待收、拒收。

外部的入库 6 态、出库 7 态、工序 4 态、SLA 三态统一收敛到上述两组 5 值，不另立枚举；SLA 临期与超期以列值展示，不占状态页签。

### 4.3 配置驱动作业

单据工序编排 → 工序库与工步 → 任务拆分维度、尾差归集、缓冲节点、数量守恒 → 派工权重（负荷／区域／连续性／排队／班次）→ 执行单元承接任务类型与人员资质。配置层对象不带仓维度：外部用 `config-scope.mjs` 在构建期从引用链派生适用仓，本项目按「单仓端即一座仓」直接落在本仓配置页，行带 `data-owner` 表达货主维度，不搬派生链。

### 4.4 单仓数据范围

外部：页头「仓库」下拉切换 8 个实体仓，`[data-wh]` 行过滤。本项目：单仓端产物就是一座仓，不提供仓库下拉、不提供主体切换器；顶栏「货主」下拉 + 行上 `data-owner` 表达多货主业务维度（仅仓网管理端、单仓端允许），跨仓数据归仓网管理端，货主端按登录身份限定数据。

## 5. 关键流程

三条链共用「单据 → 任务 → 库存账」骨架，逐步骤列出异常分支与逆向回路；状态名取 `glossary.md` 第 3 节。

| 链 | 步骤 | 输入 | 产出／状态 | 异常分支（触发 → 动作 → 归宿） | 逆向 |
| --- | --- | --- | --- | --- | --- |
| 入库 | 1 委托受理 | 货主入库委托 | 入库通知单 `pending` | 必填缺失／商品未发布／仓库不支持该作业类型 → 驳回并留痕 → 退回委托 | 未收货前可取消至 `cancelled` |
| 入库 | 2 到货登记 | 通知单、到货月台 | 到货次数、预计到货时间 | 无单到货／重复登记 → 挂起并登记异常 → 待人工确认 | 撤销登记，通知单回 `pending` |
| 入库 | 3 收货验收 | 通知单明细、扫码 | 批次、实收／拒收、差异 | 短收、超量、批次或效期不符、跨货主串货、扫码故障 → 拒收或挂起、登记差异、告警 → `exception`；零条或多条条码命中判异常，不取其它货主主档 | 错收冲销入库台账，走退仓逆向单据 |
| 入库 | 4 上架 | 上架任务、推荐库位 | 目标库位、上架数量 | 库位占用／容器冲突／执行单元不匹配 → 改派或改库位 → 任务回 `wait` | 反上架回退库存与库位占用，留原单据行 |
| 入库 | 5 记账 | 实收、上架结果 | 库存台账、批次效期 | 数量不守恒 → 拦截并登记差异 | 已记账用调整任务冲正，不删原流水 |
| 出库 | 1 受理 | 货主出库委托、商城订单 | 出库订单 `pending` | 库存不足／禁售过期批次／货主资质不符 → 驳回 → 退回委托 | 未释放前可取消 |
| 出库 | 2 波次与分配 | 订单、截单时间 | 波次计划、锁库 | 波次容量超限／并发占用 → 拆波或转人工 → 回待分配 | 释放波次、解锁库存 |
| 出库 | 3 拣货复核 | 拣货任务、扫码 | 已拣数量、包裹 | 拣货差异、错拣跨货主、设备与扫码故障 → 登记异常、挂起 → `blocked` | 部分完成后发起取消，走返仓回上架 |
| 出库 | 4 发货交接 | 包裹、承运商 | 交接单、运单 | 交接数量不符／运单失败 → 挂起并重试 → 回 `busy` | 逆向交接：退货、退仓入库，原出库单不删 |
| 出库 | 5 完成 | 交接回单 | 单据 `completed`、库存扣减 | 回单缺失 → 保持 `doing` 并告警 | 已完成为不可逆终态，只能走退货逆向单 |
| 库内 | 1 生成单据 | 策略触发／人工／盘点差异 | 移库单、补货单、盘点单 | 触发条件不满足／重复生成 → 拦截并留痕 | 未审核前撤回 |
| 库内 | 2 拆任务 | 编排、拆分维度、派工权重 | 移库／补货／盘点任务 | 无可用执行单元、人员无资质、班次缺员 → 转人工派工 → 待指派 | 撤销派工，任务回 `wait` |
| 库内 | 3 执行 | 任务、库位、容器 | 实移／实盘数量 | 目标库位冲突、容器占用超时、盘点差异 → 挂起、登记异常 | 差异复盘、二次盘点回初盘 |
| 库内 | 4 记账 | 差异确认结果 | 库存调整、台账流水 | 差异未确认／审批驳回 → 挂起 | 调整任务冲正，保留原实盘与原流水 |

**不可逆与留痕**：已完成且已记账的单据、已交接的出库单、已确认并记账的盘点差异为不可逆终态，只能新建逆向单据（退货、退仓、冲销、调整任务）处理；取消、撤回、反审核、返仓、退货都保留原单据行、任务行、扫码原值、货主、批次与时间戳，不物理删除。异常处置一律写明触发条件、处理动作与归宿状态，不留悬空分支。

## 6. 界面结构说明

### 6.1 外壳与导航

单仓端用 `admin` 外壳（`wx-app`）：顶栏为产品名、端名副标题、全局搜索与账号会话；侧栏按模块分组列本端页面，条目文案取 `pages[].name`；页头页签按模块成组，只列本端页面，不生成跨端或跨模块链接。顶栏「货主」下拉与页头「货主」作用域标签可用，不出现仓库下拉、主体切换器、租户相关控件。

### 6.2 五类骨架分工

| 骨架 | 三段里的页面 | 结构 |
| --- | --- | --- |
| `list` | 全部单据台账、任务台账、9 页配置、波次计划、库区库位 | `statusTabs → filters → toolbar → table → pager`；计数放 `statusTabs` 的 count，不加统计卡片与页内大标题，不写自绘筛选栏 |
| `detail` | 入库通知单详情 | `DetailPage` 分基础信息、明细行、实收汇总、任务四段 |
| `report` | 单据总览、作业看板 | `ReportHero + StatRow + Block`，展示在办合计、异常与超期、工序节点负载、窗口告警 |
| `scan` | 收货验收、拣货作业、盘点作业 | `ScanPage`；先有单据或任务上下文（单号、货主、操作员、设备、库位），再扫商品与批次 |
| `shop` | 不用于单仓端 | 只给 `shell = "mall"` 的商城端 |

### 6.3 页内结构

- **单据／任务列表页**：状态页签取第 3 节枚举，首个为「全部」，其余页签必须带 `field` + `value` 真筛；筛选项的 select 选项从行数据派生；数字列右对齐；工具条按状态显隐主操作（提交审核、审核通过、批量确认、批量异常登记、取消）；行上挂 `data-owner` 与状态字段。单据与任务合页的页面以任务执行为主视角，来源单据号作为一列。
- **配置页**：一页一表，状态页签取 `作业资源状态` 枚举；外部「左栏清单＋右栏详情」「页内多视图」一律收敛为列表页加关键字段列，不引入 `data-view-panel`。
- **报表页**：允许 `ReportHero` 与 `StatRow`，口径说明用 `tipKey` 进 `title`，不把解释性长句摆到版面上。
- **扫码页**：对象摘要含第 N 行、货主、商品编码、批次；PDA 次操作「下一件」、主操作「确认」。

### 6.4 交互驱动对照

| 外部 | 本项目 | 说明 |
| --- | --- | --- |
| hash 路由 + `[data-ctx]` 三级页签 | 页头页签切页 + `data-*` 属性 | 端产物仍是一份 HTML，按页显隐 |
| `[data-wh]` + 页头仓库下拉 | `data-owner` + 顶栏货主下拉 | 仓库维度由端本身限定 |
| `[data-doc]` 单据详情抽屉 | `detail` 页 + `data-*` 行属性 | 不用挂 `body` 的抽屉，避免跨页隐藏 |
| `[data-view-panel]` 页内多视图 | 拆成独立页或一页主表 | 骨架不许混搭 |
| `[data-status-tab]` + `data-<field>` | `statusTabs` 的 `field` + `value` | 页签必须真筛 |
| `[data-toast]` 原型示意 | `data-toast`，文案「动作名（原型示意）」 | 取 `glossary.md` 第 5 节 |

所有可见文字（页面名、页签、列名、按钮、状态、空态、分页单位）逐字取 `glossary.md`；`StatusTag` 与 `StatRow` 的取值不超出第 3 节枚举；页面模块只写 `columns` / `rows` / `filters` / `toolbar`，只 import `../../shared/ui.mjs`，不写 `<script>`、不写死 hex、不跨模块 import。
