3. 未回答的结论栏写「待答」；结论推翻建议时，在影响面里写明连带要改的既有口径。
4. 一轮答完再进下一轮，问题不跨轮次重排。

## 第 1 轮（2026-11-07）

本轮三个问题都来自 `humanfile/功能结构描述.md` 与现有单据口径的冲突点：订单分发、一件代发的货权链、部署形态。

### Q1-1 仓网端「订单分发」到底分到什么粒度

**问题**
仓网端说的「订单分发」，是「计划单确认后按单头目标仓 1:1 下发到仓」，还是要「系统按库存、时效、成本自动选仓」，甚至「一张销售单或平台订单拆到多个仓发货」？

**建议**
一期沿用「确认即 1:1 下发」，选仓做成「系统给建议仓 + 人工确认」，不做自动拆单。

理由：
- 现有 `出库计划单.targetWarehouse` 定在单头且确认后不可改，锁库按「商品 × 批次 × 仓」全量冻结，SLA 按「仓 × 货主 × 出库」取快照。拆单要同时改锁库、时效、对账三处。
- 平台订单是单包裹单地址，拆仓会产生多包裹多运单，`商城订单.obNo` 只有一个字段，装不下多个履约单。

**结论**
按 1:1 下发。系统给建议仓、人工确认，不做自动拆单。

**影响面**
若维持 1:1：只需在 `计划单与时效协议方案.md` 第 4 节补一句「选仓建议不作为分发对象」。
若改为自动选仓：`出库计划单.md` 的 `targetWarehouse`、`lockStatus` 与锁库章节要重写。
若改为拆单：`商城订单.md` 的 `obNo` 要改一对多，`出库订单.md` 的履约映射表要重画。

### Q1-2 一件代发要不要「代发采购单」这一层

**问题**
卖家在平台开了店但没有货、到货源商城找货代发这条链，中间要不要一张「代发采购单」，还是让平台订单直接落到货源方的出库计划单？

**建议**
要这一层。链路定成：平台订单 → 代发采购单（在货源商城下单）→ 货源方出库计划单 → 出库订单 → 直发终端消费者。

理由：
- 结算与分账要分开：终端付给卖家、卖家付给货源方，两笔钱不能混在一条单据上。
- 退货归属要能追：终端退回时，要能判断退给卖家还是退给货源方，没有采购单这一层就断链。
- 库存承诺在货源方，锁定发生在货源方的计划单上；缺采购单，平台订单与货源方库存之间没有对账依据。

**结论**
加。链路为 平台订单 → 代发采购单 → 货源方出库计划单 → 出库订单 → 直发终端。已在 Q5-1 确认。

**影响面**
新增「代发采购单」实体并登记分类索引与日志；`商城订单.md` 要区分「买家自购」与「代发」两种；`出库订单.md` 的收货方从买家货主改为终端消费者；`入库计划单.md` 的售后入库来源要能回指终端退货。

### Q1-3 货主端单独售卖时的部署形态

**问题**
货主端作为「单独卖软件」的产品交付时，是一套部署服务多个卖家（多主体、数据强隔离），还是一套部署对应一个卖家或一个运营方（单主体，多个货主只是业务维度）？

**建议**
一期保持单主体：产品可以复制成多份交付，但每份部署只服务一个运营方，货主仍是业务维度。

理由：
- 现有账号、权限、数据可见范围全按「单主体 + 货主为业务维度」设计，`skuCode`、库位编码、单据号都是全局唯一的单主体口径。
- 转多主体要动编码规则、唯一索引、权限模型、账单归属，属重写级改动，不是加字段。
- 要卖多份时，「一套部署一份」比「一套部署服务多主体」成本低得多，也不破坏现有验收。

**结论**
待答。负责人明确「货主端是 SaaS」；SaaS 边界已在 Q2-3 澄清为「只有一个运营方、一套仓网」，不存在多运营方情形。真正的待定项改为「货主如何进入系统」，转入第 3 轮。

**影响面**
若只有货主端 SaaS：货主端要加主体维度，仓网端与单仓端保持单主体，两层的「货主」要分开定义，`货主主档` 不能再一处定义两用。
维持单主体：在 `CODEBUDDY.md` 与工作区规则里把「货主端可单独交付」与「非多主体」两句话写在一起，避免后续误读成要转多主体。
若转多主体：`货主主档.md`、`商品主档.md`、`子账号.md` 的唯一约束与可见范围全部要改，`docs/` 内所有单据号规则要复核，原型外壳的登录与会话层要重做。

## 第 2 轮（2026-11-07）

本轮三问是对第 1 轮 Q1-2、Q1-3 的追问，目的是先定「入驻型指哪一侧」「外部平台订单怎么落」「SaaS 边界」。

### Q2-1 「平台做成入驻型」指哪一侧

**问题**
「平台都做成入驻型了」这句话里的平台，指外部电商平台（Temu、Amazon、Shopee），还是指我们的货源商城？

**建议**
如果指外部平台，入驻型是平台侧的事，不改变订单归属，我们仍要把订单拉回来才能履约；如果指货源商城，订单在我们侧产生，走商城订单，不需要平台订单。

**结论**
指货源商城。外部商家入驻开店，订单在我们侧产生，走商城订单。

**影响面**
货源商城要有一条商家入驻链路，可复用现有 `企业资质认证`、`店铺`、`商城商品`；商城渠道的订单仍按 `sourceDocType=商城订单` 落。外部平台渠道不受这条影响，另按 Q2-2 处理。

### Q2-2 外部平台订单怎么落

**问题**
接外部的 Temu、Amazon 等平台订单时，是建独立实体，还是只在出库计划单上加平台与平台单号字段？

**建议**
建独立实体。退款、取消、改地址这些变更发生在平台侧，没有实体就没有地方落平台状态与同步时间，多平台数据一致性无从对账。

**结论**
建独立实体：存平台、店铺、平台单号、平台状态、同步时间与退款状态，出库计划单回指它。

**影响面**
新增「平台订单」实体并登记分类索引与日志；`出库计划单.md` 与 `出库订单.md` 的 `sourceDocType` 加「平台订单」；平台订单与商城订单并列，不合并成一个实体，两者只是都汇到同一张出库计划单；平台状态与本地履约状态之间要一张映射表。

### Q2-3 货主端 SaaS 的边界

**问题**
货主端 SaaS 是一套部署服务多个 3PL 运营方，还是一套部署对应一个运营方、下挂多个卖家货主？

**建议**
原建议为「一期单主体、一套部署一份」。该建议基于对 SaaS 的理解有误：把 SaaS 等同于多运营方。

**结论**
仓网端只有一家运营方，不存在多运营方的情形，本问前提错误、问题作废。

**影响面**
单主体模型维持：`ownerName` 单外键、编码规则与唯一约束都不加主体维度，现有按货主隔离的数据边界可直接复用。SaaS 改变的只是货主进入系统的方式，该点转入第 3 轮 Q3-1。

## 第 3 轮（2026-11-07）

本轮三问：货主怎么进入系统、代发要不要中间单据、仓储费与 SaaS 费怎么记账。

### Q3-1 卖家货主怎么进入系统

**问题**
卖家货主是自助注册即开通，还是由运营方开号，还是注册后要审核。

**建议**
自助注册 + 运营方审核开通。仓是实体服务，不能注册完就能往仓里发货。

**结论**
货主端更名为「货灵ERP」。用户可以直接注册，付费即可使用；需要仓网的仓储服务时，要与仓网签约后才能使用。

**影响面**
- 产品名与端名要改：`glossary.md` 的端名与页面名、`CODEBUDDY.md`、原型外壳标题、`modules.json` 的 `apps[]` 名称。
- 「货主」要拆成两个概念：货灵ERP 注册用户（可能只买软件、不签约）与签约货主（有仓储服务关系），现有字典把所有单据都挂在 `ownerName` 上，默认 owner 就是仓的客户，这个默认要改。
- `货主主档.md` 要补签约状态或另建签约关系；未签约用户不能建入库计划单、出库计划单，点进去应引导签约。
- 权限与数据可见范围按签约状态分层，`子账号.md` 的可见业务范围要加「未签约」口径。

### Q3-2 需要平台订单这一层么

**问题**
接外部电商平台时，到底要不要「平台订单」这一层。上一轮把「平台订单」与「仓储单据」混在一起讲，负责人要求先给出明确判断。

**建议**
要，但归属要说清：平台订单属于货灵ERP 的订单中心，不属于仓储单据链。仓储侧只认出库计划单，计划单记「来源=平台订单 + 平台单号」，不承载平台状态。平台侧的退款、改地址、取消在 ERP 侧闭环，仓储不感知。

**结论**
归货灵ERP 的订单中心，不进仓储单据链。已在 Q4-1 确认。

**影响面**
若按建议：`平台订单` 实体落在货灵ERP 的订单中心，`docs/数据字典/` 要新增该实体，但 `入库计划单`、`出库计划单` 只在 `sourceDocType` 加「平台订单」、`sourceDocNo` 存平台单号，不复制平台字段。
若不建：外部平台订单只能靠人工录进商城订单或直接建计划单，多平台数据一致性无法对账。

### Q3-3 SaaS 服务费与仓储费怎么记账

**问题**
货灵ERP 的服务费与仓储费是两套账还是一张账单。

**建议**
两套账分开。仓储费走现有费用账单，SaaS 服务费单独一张账。

**结论**
两套账分开。

**影响面**
`费用账单.md` 的计费方式要加「按账号 / 按月」，费用项目不加 SaaS 项；另建 SaaS 账单或账单类型，开票主体与账期可与仓储账单不同；货主端账单页要分成两个入口，避免一张账单混两类费用。

## 第 4 轮（2026-11-07）

本轮三问：平台订单归属、未签约用户范围、签约关系落在哪个实体。三问均按建议结论通过。

### Q4-1 平台订单算哪一层

**问题**
平台订单归货灵ERP 的订单中心，还是也进仓储字典，还是干脆不建实体只加字段。

**建议**
归 ERP 订单中心。平台订单存平台状态与退款，进数据字典；仓储侧只记来源与平台单号，不复制平台字段。

**结论**
归 ERP 订单中心。

**影响面**
`docs/数据字典/` 新增「平台订单」实体并登记分类索引与日志；`出库计划单.md`、`出库订单.md` 的 `sourceDocType` 加「平台订单」，`sourceDocNo` 存平台单号；平台状态与本地履约状态之间要一张映射表；仓储端页面不展示平台状态与退款字段。

### Q4-2 未签约注册用户能用什么

**问题**
只买货灵ERP、没跟仓网签约的用户，能用哪些功能。

**建议**
只能用 ERP 功能：订单、刊登、库存查询可用；入库计划单、出库计划单建不了，入口引导签约。

**结论**
只能用 ERP。

**影响面**
货主端菜单按签约状态显隐，计划单入口置灰并给签约引导；`子账号.md` 的「可见业务范围」要加未签约口径；原型要加一个未签约的演示身份或签约状态，否则这条分支没法验；`货主主档.md` 与签约关系要能判定「是否签约、签了哪些仓」。

### Q4-3 签约关系怎么落

**问题**
货主与仓网的签约关系，是新建实体、复用时序协议加状态，还是只在货主主档加一个字段。

**建议**
新建「仓储服务协议」，绑货主与仓网，含签约状态、服务仓库范围、生效期，支持一个货主分仓陆续签约。

**结论**
新建仓储服务协议。

**影响面**
新增实体并登记索引与日志；`货主主档.md` 不再承载签约状态，只在关系节引用协议；`时效协议.md` 与它分工要写清：协议管商务关系与服务范围，时效协议管作业承诺，两者按「仓 × 货主」对齐但不合并；计划单提交时校验「目标仓已签约」，未签约不允许提交。

## 第 5 轮（2026-11-07）

本轮三问：代发要不要中间单据、WCS 做到哪一层、改名改到什么范围。三问已定，其中第二问推翻了 `humanfile/功能结构描述.md` 对单仓端的定位。

### Q5-1 一件代发要不要代发采购单

**问题**
卖家无货、到货源商城找货代发，中间要不要一张代发采购单。

**建议**
要。链路定成 平台订单 → 代发采购单 → 货源方出库计划单 → 出库订单 → 直发终端。

**结论**
加代发采购单。

**影响面**

### Q5-2 单仓端的 WCS 做到哪一层

**问题**
单仓端定位是 WMS + WES + WCS 的合集，WCS 这一层要不要建模设备指令下发与任务队列。

**建议**
任务派工为止：任务派给人或设备，设备回传完成状态，异常人工介入，不建设备指令下发与队列。

**结论**
任务派工为止。

**影响面**
`工序单.md`、`设备档案.md`、`执行单元档案.md` 维持现有口径，任务可归设备作为执行主体已能表达。单仓端定位从「WMS + WES + WCS 合集」收窄为「WMS + WES」，WCS 只做设备接入与状态回传，不接硬件协议。`humanfile/功能结构描述.md` 第 3 节的表述与这条结论不一致，humanfile 只读、不回改，以本记录为准。

### Q5-3 货灵ERP 改名改到什么范围

**问题**
货主端更名为货灵ERP，是只改展示名，还是连端 key 一起改，还是暂不改。

**建议**
只改展示名，端 key 与模块名不动，构建与验收不受影响。

**结论**
连端 key 一起改：`owner-app` 改为 `erp-app`，同步 `modules.json`、构建脚本、验收脚本与产物文件名。

**影响面**
要动的文件：`prototypes/shared/modules.json` 的 `apps[]`、`prototypes/build-app.mjs` 的端装配与产物命名、`.codebuddy/skills/huoling-proto/scripts/verify-delivery.mjs` 的 `--app` 取值、`references/core/glossary.md` 的端名、`CODEBUDDY.md` 与 `docs/` 内所有「货主端」表述。产物文件名「货主端.html」改为「货灵ERP.html」。改完必须重建五端、重跑全量验收，`--app owner-app` 的旧参数失效。

### Q6-2 代发采购单在货源方侧怎么呈现

**问题**
代发采购单是只在卖家侧出现，还是货源方也要处理，在哪一端处理。

**建议**
货灵ERP 里接单。货源方在自己的货灵ERP 看到采购单，确认后生成出库计划单。

**结论**

## 第 14 轮（2026-11-08）

本轮收口端名与 ERP 运营后台边界。

### Q14-1 仓网管理端是否更名

**问题**
仓网管理端现在同时管仓网、ERP 开通、平台应用、商城运营与账号权限，是否更名？

**建议**
更名，只改显示名，不动 app id、模块目录与页面 key。

**结论**
仓网管理端更名为「货灵运营中台管理端」。

**影响面**
`modules.json` 端名、glossary/registry 端名与产物路径、页面 `所属端`、现行文档端名；旧产物删除，历史日志与旧问答保留原名。

### Q14-2 商城端与单仓端是否同步更名

**问题**
商城端与单仓端是否统一货灵品牌？

**建议**
统一。

**结论**
商城端更名「货灵商城」，单仓端更名「货灵WMS」。

**影响面**
产物文件名、文档端名、页面 `所属端`；app id 与页面 key 不动。

### Q14-3 仓网管理端是否包含 ERP 管理后台

**问题**
仓网管理端是否包含 ERP 的管理后台？

**建议**
包含 ERP 运营/租户后台，但不管理货主子账号。

**结论**
货灵运营中台管理端新增「ERP 运营」五页：货主开通、模块与版本、平台应用、同步健康、全局审计；代维只读并留审计；货主子账号仍在货灵ERP管。

**影响面**
新增 `erp-ops` 模块与五页；运营中台导航增至 10 段；页面文案避开「租户」「套餐」「订阅」，统一写「货主开通」「模块与版本」。

### Q14-4 两个权限域怎么分

**问题**
ERP 货主账号与运营中台账号是否一套账号池？

**建议**
按产品域拆分，不共享登录。

**结论**
货灵ERP只管货主账号与角色；货灵运营中台管理端只管运营方与仓内账号；同一自然人跨域开两个账号；账号唯一性按 `accountDomain + accountId`。

**影响面**
运营中台账号页删除 `ow.*` 货主账号与货主角色选项；账号日志不含货灵ERP；全局审计单独放在「ERP 运营」下，可出现货灵ERP端。
