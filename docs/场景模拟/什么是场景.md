# 什么是「场景」（基础定义 · 产品经理视角）

> 本文件是「场景模拟」分类的概念基座。所有 SC 文档先读这里，再动手写。场景实例会反复改，但本定义尽量稳定。

## 1. 一句话定义

**场景（Scenario）** 是需求/能力的「实例化载体」：把一条抽象能力，落到「谁、在什么条件下、用系统的哪一端、做什么动作、达成什么结果、可能怎么出错」的具体情形中。

它是我们做设计、做评审、做验收的最小可闭环单元——比需求具体，比用例（Use Case）更贴一次真实发生。

## 2. 它和邻近概念的区别

| 概念 | 一句话 | 与场景的关系 |
| --- | --- | --- |
| 需求 / 能力 | “系统要支持 X” | 声明“要有什么”；场景展示“X 是怎么被用起来的” |
| 用户故事 | “作为 A，我想 B，以便 C” | 一行意图；场景把它展开成带步骤与分支的叙述 |
| 用例（Use Case） | 面向目标的一般化交互 | 用例是抽象目标；场景是目标下的一条具体路径/实例 |
| 业务流程 / 任务流 | 跨角色、跨端的过程 | 流程是纵切面；场景是从某个角色座位切进去的一段 |
| 任务（如作业任务） | 系统里可执行的工作单元 | 场景描述“人+系统围绕任务的交互”，不是任务记录本身 |

**判定它是否算一个场景**：有具体角色、在操作系统的某一端、朝一个目标、有可观察起点与终点、并可能失败。纯概念、或无角色/无系统交互的，是原则或需求，不是场景。

## 3. 场景的解剖结构（所有 SC 文档的统一骨架）

一份场景至少包含以下部分（缺失即不完整）：

1. **场景描述** — 这是什么情形，解决/展示什么。
2. **参与角色** — 谁参与；每个角色锚定到「端 + 角色」（见第 4 节）。
3. **触发条件** — 什么事件/状态让这个场景开始。
4. **正常流程** — 主干步骤（happy path）。
5. **异常流程** — 每一步可能怎么失败、怎么处置（按 流程图规范 必须画出，不能只写文字）。
6. **闭环条件** — 什么算“做完/关闭”。
7. **闭环验证** — 可独立勾选的断言，证明它真的闭环（不看别的场景也能验）。
8. **流程图** — 一张覆盖 正常 + 异常 + 逆向 的图（业务流程图/泳道图/状态流转图均可）；逆向回路须标明从哪发起、条件、回到哪、哪些留痕不可删。

> 当前 SC 文档先有前 7 节；「流程图」一节为待补项，补完后 `check.mjs` 会把「流程图」列为必检章节。

## 4. 场景与「端」的关系（关系到怎么枚举）

每个场景必须锚定一个**端**，因为同一业务事件在不同端有不同的用户操作路径。本项目端清单（见货灵产品矩阵）：

- **作业 APP（PDA）** — 现场作业人（拣/上架/盘点/补货）的操作场景。
- **货灵WMS** — 仓内管理（主管派工、波次、出入库、异常处置）的操作场景。
- **货灵ERP** — 订单/履约/档案类操作场景。
- **货灵商城** — 开店/下单类操作场景。
- **运营中台管理端** — 货主开通、全局配置类操作场景。

**枚举口径：场景 = 端 × 用户操作 × 目标。** 同一件事（如“拣货做到一半换人”）可能涉及多个端（PDA 上的甲/乙交接领取、WMS 上的主管派工与异常授权），因此一个业务主题可拆出多份锚定不同端的场景，彼此通过「共同来源要求」关联，但不合并成一份。

## 5. 场景的粒度

- 一份场景 = 一个角色在一个端上、为达成**一个目标**、走完一条可闭环路径（含异常/逆向）。
- 过粗：跨多个目标或多个端揉成一份 → 难以独立闭环验证。
- 过细：单步点击/单字段 → 失去“情形”的意义，退化为操作手册。

## 6. 场景的稳定性 vs 实例的可变性

- **本定义稳定**：构成场景的要素（角色、端、触发、正常/异常、闭环）基本不变。
- **场景实例可变**：具体 SC 文档会随设计推演反复改 N 次；改的是内容，不是骨架。所有改动记入 `log.md`，不靠记忆。

## 7. 来源与凭据

场景模拟的来源文章、链接、访问日期与「SC ↔ 文章小节」映射，统一登记在 `log.md`，不在场景文档内重复铺陈（保持文档只讲“情形”本身）。
