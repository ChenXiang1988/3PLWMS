# 场景描述方法（写法手册 · 产品经理视角）

> 本文件是「场景模拟」分类的写法手册，配合 [什么是场景.md](什么是场景.md)（定义"什么是场景"）使用。下方结论综合了互联网上产品经理与需求工程的主流写法（见文末「参考来源」），目的是把"怎么描述一个场景"从个人习惯变成可复现的规范。

## 1. 一句话结论

描述一个场景 = 把「**谁，在什么约束下，为了什么可观察的目标，按什么顺序做了哪些动作，可能怎么出错，最后怎么算完**」写清楚。主流实践把它收敛为**四要素**：**角色、目标、触发条件、任务流程**，再按需补充**前置条件、环境/约束、异常分支、完成标志**。

## 3. 每节写法细则

### 3.1 场景描述
- 用「作为【角色】，在【境/约束】下，为了【目标】…」或「【角色】在【环境】遇【痛点】，希望【行动】以【期待】」（EPAE 叙事）起头，一句话讲清这是哪段真实情形。
- 不要写成功能列表（"支持换人"），也不要写成用户画像（"中年仓管"）。

### 3.2 参与角色
- 每个角色写清：身份 + 在场景里承担的具体动作与判断 + 锚定到哪个端（见 [什么是场景.md](什么是场景.md) §4）。
- 区分主要参与者（主动追求目标）与次要参与者（被动卷入，如系统、审批人）。

### 3.3 触发条件
- **前置条件**：场景开始前必须为真的状态（如"任务进行中、甲已完成 40 箱"）。
- **触发事件**：让场景开始的事件 / 时间 / 状态变化（如"主管发起换人"）。
- 两者共同界定场景的起点。

### 3.4 正常流程
- 编号步骤；粒度以"一个动作对应一个可观察操作或决策"为宜。
- 每步建议写清：**输入**（来自上一步 / 系统 / 环境）→ **动作**（角色做了什么或系统做了什么）→ **产出**（状态 / 数据 / 交接）。
- 在跨角色交接点标注"谁交给谁、以什么方式确认"。

### 3.5 异常流程
- 不要只画一根线指向"异常处理"黑盒。
- 写法：「在步骤 N，若 <条件>，则 <处理动作>，回到 <步骤 M / 终态>」。
- 优先覆盖高频与阻断性异常；每条分支写清 触发条件 → 处理动作 → 归宿。

### 3.6 闭环条件
- **成功后置条件**：场景成功结束后，保证为真的状态（如"剩余 20 箱当前负责人 = 乙"）。
- **关闭标志**：什么算正式关闭（如"任务状态 = 已关闭、差异归档"）。

### 3.7 闭环验证
- 用可勾选断言；或 Given / When / Then。
- 自检：把场景读给同事听，他能否不靠别的文档说出起点与终点。

## 4. 常见错误（写出来像"假场景"）

- 把功能列表当场景（"系统支持 XX 管理"）。
- 只写主流程，不画/不写异常与逆向。
- 角色写成抽象群体（"用户""管理员"），没到"这一步谁负责、谁确认"。
- 目标写成主观感受（"提升体验"），不是可观察完成状态。
- 缺 人 / 境 / 事 任一项 → 场景不成立（人人都是产品经理 三要素）。
- 跨多个目标或多个端揉成一份 → 难以独立闭环。

## 5. 自检清单

- [ ] 角色、目标、触发、任务流程四要素齐？
- [ ] 触发条件分了前置条件 + 触发事件？
- [ ] 正常流程每步有 输入/动作/产出，交接点有确认？
- [ ] 异常流程用"步骤 N 若…则…回到…"，覆盖高频/阻断项？
- [ ] 闭环条件区分了后置条件与关闭标志？
- [ ] 闭环验证是别人能独立勾的断言？
- [ ] 读给同事能说出起止？
