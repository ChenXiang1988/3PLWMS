八条结论

一、两家客群几乎不重叠：店小秘做多平台铺货的宽度，领星做亚马逊单店的深度。
二、定价锚点就是战略：店小秘卡店铺数，领星卡订单量；被惩罚的行为分别对应「开很多店」与「出很多单」。
三、店小秘的财务是「够用的毛利估算」——按发货时点、17 平台自动取费、其余手动导入、6 个平台完全不支持利润核算。
四、领星的财务是「可审计的核算」——三种收入确认口径、五种延迟结算状态、15 个收支科目、可与亚马逊 Transaction 报告逐笔核对。
五、店小秘的护城河是平台适配的广度与运维：30 篇订单文档里 14 篇是平台专项，平台 × 托管模式逐条拆。
六、两家的订单都停在「把这一单推出去」：店小秘靠审单规则打标记，领星靠 8 类失败原因兜底，都不记录「为什么这么决定」。
七、货灵要同时做铺货与履约，前提是补一层电商商品模型（SPU → 变体 → 平台 Listing → 仓储 SKU），否则两条路径会各建一套商品。
八、开源侧没有可用的跨境 ERP，不构成竞争威胁；但 Odoo/ERPNext 是真实的自建基线，构成 3–5 万元/年的定价上限。

01调研背景

货灵ERP 是产品群里的获客入口，单独售卖给跨境电商卖家，客群为铺货卖家与直做 POP 卖家B。它面对两类对手：多平台铺货工具（店小秘）与单平台精细化运营系统（领星）。

此前的资产只有店小秘的逐页实测记录，领星仅到菜单层；定价维度两家都缺。产品定位、功能取舍、免费版边界都没有可以对照的量化依据，导致方案讨论停留在「应该做什么」，而不是「别人卡在哪、我们卡不卡得起」。

本次把两家拉到同一张表上，补三块：领星的功能深度、两家的定价结构、由定价反推的产品战略。

05市场结构

中国跨境电商 ERP 不是一条连续光谱，而是按「平台策略」分成几个互不重叠的阵营。同一个卖家不会同时是两家的目标客户。

阵营代表核心命题产品形态特征
多平台铺货店小秘、马帮、芒果店长怎么用最低成本把货铺到最多平台刊登与采集重、平台覆盖广、单量大客单低、免费版承担获客
单平台精品领星、积加、赛狐怎么把单店单 SKU 的利润与广告效率做到极致广告与财务深、BI 强、按量计费、客单高
供应链与仓配马帮、易仓怎么管住采购、头程、海外仓采购与仓配重，适合有自建供应链的卖家
全渠道中台聚水潭、旺店通国内电商与跨境订单统一处理订单中台强、跨平台库存统一
开源 / 自建Odoo、ERPNext、启航能不能不买 SaaS，自己搭一套通用底座完整但跨境能力靠连接器，无开箱即用方案，见第 9 章

阵营划分依据为各家官方定位与公开客群描述C；店小秘与领星的归类有菜单结构与定价锚点佐证AB。

货灵现有 12 段导航（工作台 / 订单 / 履约 / 售后 / 仓储委托 / 异常与对账 / 库存 / 商品 / 商城店铺 / 平台接入 / 账单与服务 / 报表与设置）不属于任何一列：有铺货的订单入口，有精品的履约深度，还有两家都没有的仓储委托与商城店铺。这个结构是差异化的起点，也是必须选边的原因——不选边就在每个阵营里都排第三。

6.3 订单能力

订单是打单流水线状态机，围绕「把这一单打出来发走」组织：

全部 · 待审核 · 待处理 · 运单号申请 · 待打单 · 有货/缺货 · 已交运 · 发货失败 · 发货成功 · 已退款 · 已搁置A

异常不是独立单据，是列表筛选条件，共九类A：有备注、有留言、买家指定多物流、报关信息未填写、俄罗斯收件人非全名、缺货、未配对 SKU、仓库无此 SKU、黑名单买家。小团队用起来有效——不用切页就能处理；但它不能回答「这个异常是谁造成的、什么时候必须解决、超时谁负责」。

审单规则四个页签：审单规则、物流规则、赠品规则、运单号自动申请规则，另有自定导出A。结构是「优先级 + 条件 → 动作」，有规则试算与系统规则两层。页面提示语写明用途是「将订单移入待审核并打上对应的标记/备注」。

这是一个分流器，不是决策记录器：命中后只留标记，不记录为什么这单走了这个仓、这个承运商。规则试算值得借鉴——它把「配错了会怎样」提前暴露。

7.6 财务能力

本次调研里最被低估的一块。利润报表支持三种收入确认口径，每种都能与亚马逊原始报告逐笔核对B。

口径确认时点延迟订单处理适用场景
按结算时间亚马逊实际释放、进入店铺余额实际释放后计入只关注实际到账
按结算时间（含预结算）已发放 + 符合规则的预结算本月应结未结的提前计入，实际结算后自动冲销利润要及时反映当月经营
按发货时间订单发货时间（Transaction 报告 Date/Time）按发货口径核算，不依赖后续释放，不产生冲销按发货核算且不需后续调整

延迟结算被拆成五种交易类型：已发放、已推迟、已推迟-跨月结算、已推迟-估实差异、已推迟-已入账冲销。切换口径有三个可验证后果：历史分摊配置失效需重新配对、订单维度 API 唯一键变更、历史数据从启用月重算。

收支科目拆到 15 项B：

平台收入 = 销售额 + 买家运费 + 促销折扣 + FBA库存赔偿 + COD + 其他收入
平台支出 = 平台费 + 发货费 + 其他订单费用 + 广告费 + 推广费
         + FBA仓储费 + FBA国际物流运费 + 调整费 + 平台其他费
对货灵的直接约束

「订单利润做到订单级」第一个要定的不是分摊，是收入确认时点：按发货还是按结算。时点不同，同一张订单在不同月份可能一次是利润一次是亏损；跨月结算、退款、汇率都会让数字变化。领星把它做成可配置口径，货灵至少要明确一种默认口径并写进字典。

另一个细节：文档专门解释了「为什么会出现负利润」——延迟结算让收入晚于销售时间入账，而广告费、仓储费按原时间发生。说明这套口径是从会计异常场景倒推的，不是从页面布局倒推的。

9.4 对货灵的四条结论

S1

开源不是竞争威胁，但构成定价上限

没有能直接替代商业 ERP 的开源项目，所以不必担心客户「下载一个就用」。但 Odoo/ERPNext 是真实存在的「自建基线」，中大型卖家会算这笔账。参照启航 README 的自述：自研维护需 1–2 人、年成本 30–50 万、3–6 个月熟悉代码。对照货灵专业版 8,000–15,000 元/年，自建成本是订阅价的 20–60 倍。

结论：定价区间安全，甚至可以更自信；但超过 3–5 万元/年时，中大型客户的「自建」选项会重新变得有吸引力。

依据：GitHub 检索结果A；启航 README 的自研成本自述B。
S2

开源项目的死法印证「ERP 是运维生意」

metasfresh 每天提交但三年不发版、FJ-OMS 高 star 零 issue、bibi 停更九年仍挂着跨境全栈的名头。这三件事说明：写代码不是壁垒，持续把平台变化接住才是。店小秘 70+ 平台、1700+ 物流渠道的运维积累，在这条逻辑上被开源侧独立验证。

对货灵的含义：要建的不是功能数量，是运维能力——适配器版本发布、同步健康、失败重试、游标续传。这些在方案里是「能力层」，在竞争里是「护城河」。

依据：GitHub API 的 pushed_at 与 releases 对照A；店小秘平台适配广度A。
S3

可借鉴的架构是 OpenLinker，不是 Odoo

OpenLinker 的六边形架构把每类外部系统抽成能力端口：OrderSourcePort（订单接入）、ProductMasterPort（商品主数据）、InventoryMasterPort（库存）、ShippingProviderManagerPort（承运商）、InvoicingPort（开票），每个端口下挂平台适配器，用 dispatchCapability<T> 分发。这与货灵的 platformCode × orderTypeCode 配置矩阵是同一思路，且比货灵现有方案更彻底——它把「能力」而非「平台」作为第一等公民。

Odoo 不适合当底座：5.5 万 star、1.1 万开放 issue、300+ 模块，改造成本高于收益。可借鉴的只是它的配置化思想（服务端配置驱动界面显隐），不是代码。

依据：OpenLinker README 与端口清单B；货灵现有平台适配器方案A。
S4

「没有 SPU 层」这个空位，开源侧同样存在

第 8.3 节发现店小秘与领星都没有 SPU，开源侧也一样：Odoo 最接近，但它是「产品模板 + 变体」（product template / variant），解决的是同一商品多规格，不是「一个商品 → N 个平台 listing」；OpenLinker 有 ProductMasterPort，同样不做 SPU 聚合。

一个空位在商业与开源两侧同时存在，说明它不是谁疏忽了，而是被平台差异切碎后的结构性缺口。这提高了货灵做商品中枢的判断权重。

依据：Odoo 商品模型B；OpenLinker 商品端口B；店小秘与领星配对模型AB。

10关键发现

F1

两家客群几乎不重叠

店小秘把 Amazon、TikTok、Temu 卡在付费墙后、放开速卖通，要的是从速卖通起步的铺货卖家。领星反过来，亚马逊功能全量开放到月单 5,000，要的是已经在亚马逊出单的精品卖家。两家的产品深度与免费策略互相排斥，一个卖家很难同时是两家的目标客户。

依据：店小秘免费版分平台额度B；领星免费版规则B；两家一级菜单构成A。
F2

定价锚点决定产品边界，不是反过来

店小秘按店铺数收费，所以必须把多店铺管理做顺：授权、批量、跨店汇总。领星按订单量收费，所以必须把单店单 SKU 的产出算到极致：广告效率、利润口径、库存周转。如果货灵按店铺数定价却去做广告深度，或按订单量定价却去做多店批量，商业模型与产品投入会互相拖累。

依据：计费单位与核心模块强度的对应关系BA。
F3

财务深度是两家的分水岭，也是货灵最容易被低估的一块

店小秘的利润核算解决「这单赚没赚」：固定发货时点、17 平台自动取费、其余手动导入、6 平台完全不支持。领星解决「这个月赚了多少、能不能审计」：三种口径、五种延迟结算、15 项科目、与平台报告逐笔核对。前者是运营工具，后者是会计系统。货灵要做订单利润，绕不开先定收入确认时点。

依据：店小秘利润核算文档B；领星利润报表计算口径文档B。
F4

店小秘的护城河是平台适配的广度与运维

70+ 平台、平台 × 托管模式逐条拆、1700+ 物流渠道、30 篇订单文档里 14 篇是平台专项。这不是产品设计能力，是长期运营与接口维护的积累。价值在「平台改规则时用户不用改操作」，代价是用户要记 20 多条路径。

依据：帮助中心 14 分类与三级路径A；订单模块 30 篇文档结构B。
F5

两家的订单都停在「推出去」，都不记录「为什么」

店小秘的审单规则命中后只打标记；领星把审核失败拆成 8 类原因，但成功路径没有决策记录。两家都能回答「这单发货了吗」，都不能回答「为什么走这个仓、这个承运商、承诺了几号发」。中间这段是空的。

依据：店小秘审单规则页面提示语与实际效果A；领星订单管理文档的状态与异常机制B。
F6

两家都没有 SPU 层，一个商品的多平台 listing 没有共同父级

店小秘是「仓储 SKU + 产品」两套靠配对连接；领星是「本地 SKU + MSKU」1:1 配对。两者都没有 SPU，意味着同一商品在不同平台的 listing 之间没有父级，改价改库存要逐条操作。这既是两家的共同盲区，也是货灵商品中枢的空间。

依据：领星 Listing 文档的配对规则（1 MSKU : 1 SKU）B；店小秘商品管理与产品模块分离A。
F7

免费版不是试用，是产品档位

两家免费版都能长期使用，功能没阉割到不可用：店小秘订单处理不限量，领星功能与付费版相同。免费版要能独立支撑一个卖家的完整业务，否则转化与口碑双输；同时必须有限制点，否则没有付费动力——店小秘卡店铺数，领星卡单量。

依据：两家官方免费版规则B。

11货灵ERP 的定位

平台与铺货广度窄平台与铺货广度宽
订单之后的能力深领星：亚马逊精品，财务与供应链深货灵ERP：多平台 + 履约闭环 + 订单级财务
订单之后的能力浅—店小秘：铺货效率高，履约停在打单流水线
定位陈述

面向多渠道卖家的商品与履约中枢：一个商品管住所有平台的 listing、库存与订单；铺货靠它放量，履约靠它收口。

  1. 商品是地基，不是附属。一个商品在十个平台的价格、库存、上下架状态，在中心改一次，不是去十个后台各改一次。
  2. 两条路径共用一条链。铺货是「采集进来 → 批量推到 N 个平台」；履约是「订单回来 → 渠道单 → 履约单 → 执行单」。同一份商品与库存数据。
  3. 货源与仓配在同一套数据里。缺货时进商城找货源、走一件代发，货到了能进仓。这是两家结构上做不到的，因为它们没有货源和仓网。
支点能做不能吹
商品中枢一个 SPU 管多平台 listing、批量改价改库存、批量上下架不等于采集能力比店小秘强；采集来源与成功率是工程活
履约闭环决策可追溯、异常可归属、四单对账不等于仓内作业强，仓内是货灵WMS 的事
货源直连商城一件代发、工厂货源、代发采购不等于货源自营，规模取决于招商
仓配同源委托单据直连仓网、服务费同链结算只是 ERP 的一项能力，不是差异化的全部理由

采集与批量刊登做只做 1688 与链接两条来源 + 按平台发布适配，不做全渠道采集与图片处理P0–P1
订单利润（订单级）做卖家选 ERP 的硬指标；先定收入确认时点，不做分摊P0
代发采购单补强已有页面，需与商城货源打通P0
头程物流单做（轻）与仓配同源是差异化；只做单据与轨迹，不做比价P1
客服消息聚合做（聚合）只聚合订单相关消息并跳转平台回复，不做智能客服P1
广告管理不做26 个模型背后是广告 API 与指标体系的长期投入，不是页面问题—
BI 自定义报表不做固定报表覆盖九成场景；自定义是专业分析工具的事—

取舍后的页面增量：38 页 → 约 45 页。两家功能表加起来是 80+ 页，差距不在做少了什么，在商品层复用了同一份数据。

12.4 订单利润口径

项取值来源
商品售价 + 买家运费订单明细行金额 + 运费平台订单
平台佣金与手续费平台费率 × 金额，或平台回传的实际扣费平台结算 / 费率配置
物流费实际面单费用运单
采购成本代发采购价 × 数量，或仓储 SKU 成本价采购单 / 商品主档
退款已退款金额售后单
毛利收入 − 上述成本计算

不做：广告费、头程运费、包材、仓储服务费的分摊。这些的分摊维度是运营与财务口径问题，不同卖家答案不同；强行分摊会让订单利润变成没人信的估算值。

必须先定：按发货时间确认还是按结算时间确认。建议默认按发货时间——与货灵的履约单据天然对齐，且不需要处理冲销。但要把「平台结算回传后可重算」留成能力，否则会重蹈店小秘「费用侧结算滞后」的覆辙。

13商业化建议

档位店铺数月订单量3PL 委托定位
免费版1500含，月 20 单以内仓配是钩子：先用 ERP 管店，货要进仓时链路已通
标准版55,000按单计费主力档，对标店小秘 VIP1（2,016 元/年）
专业版20不限按单计费，含对账与异常对标店小秘 VIP2–VIP3、领星包年版下限

锚点选店铺数为主、订单量为辅。货灵定位多渠道卖家，店铺数是核心变量；纯按单量会把低单量多店铺的铺货卖家挡在门外，而那正是免费版要承接的人。

免费版含委托但必须限额。仓配是成本中心，无限委托等于用软件补贴仓储。20 单/月够跑通「报备商品 → 入库计划 → 出库计划 → 账单」整条链，够验证价值，不够当免费仓用。

价格带：标准版 2,000–4,000 元/年，专业版 8,000–15,000 元/年。低于店小秘同档、显著低于领星，用「商品中枢 + 履约闭环 + 货源」补差价。

自建 TCO 对照：Odoo/ERPNext 软件免费，但实施与运维的年成本在 30–50 万级（启航 README 自述：需 1–2 人维护、3–6 个月熟悉代码）。货灵专业版 8,000–15,000 元/年是自建成本的 1/20–1/60，区间安全；但定价超过 3–5 万元/年时，中大型客户的自建选项会重新变得有吸引力。这也解释了领星为什么用询价制——它面向的客群本来就会算这笔账。

订阅与服务费分账：订阅是按年预付的软件费；仓储是按委托单量的服务费，走月度账单与对账。不在同一张账单上，避免卖家把「用了仓」和「买了软件」绑死，也避免仓配亏损拖累软件定价。

14结论与建议

14.1 直接结论

对象结论
店小秘多平台铺货的宽度型选手，用免费版获客、用店铺数收费。护城河是平台适配广度与运维积累，财务是够用的毛利估算
领星亚马逊精品的深度型选手，用全功能免费到 5,000 单获客、用订单量收费。护城河是财务口径与广告体系的产品化
货灵的机会不在两家中间，在两家都缺的两处：商品没有 SPU 父级、订单没有决策留痕
货灵的前提同时做铺货与履约，必须先补 SPU / 变体 / 平台 Listing 三层商品模型
开源替代没有开箱即用的跨境 ERP，不构成竞争威胁；但 Odoo/ERPNext 是真实的自建基线，构成 3–5 万元/年的定价上限

14.2 建议（按优先级）

序动作理由前置
1建三份数据字典：SPU、商品变体、平台 Listing字段是页面与列名的真值源；字典不定，商品段 5 页做了也会返工无
2定订单利润的收入确认时点决定同一张订单在不同月份是利润还是亏损；不做分摊可以先放，时点不能空与财务确认
3商品段改 5 页，原仓储商品档案移入仓储委托段商品段要回答「卖什么、怎么上架」，不是「存什么」字典 1；跨端联动清单
4补商品配对与订单利润两个抽屉不新增页面，挂 SPU 详情与订单 360，边际成本最低字典 1、2
5定免费版委托限额口径影响开通流程与账单口径，需与仓网计费一起定仓网计费口径
6订单利润预留广告花费导入字段不做分摊不等于不记账；广告花费是真实成本，迟早要进利润表无

14.3 不建议做的事

  • 不正面拼平台覆盖。70+ 平台的运维是长期投入，只构成准入，不构成差异。
  • 不做全量采集。采集来源与反爬是工程军备竞赛，店小秘已领先多年。
  • 不做广告深度。26 个模型背后是广告 API 与指标体系的长期积累。
  • 不在没有财务口径时上订单利润页。数字对不上账，比没有这个功能更伤信任。
