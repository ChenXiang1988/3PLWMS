3.1 GrapesJS › Components / Storage Manager

入口

库以 grapesjs.init({container, plugins, storageManager}) 初始化，页面类型为画布编辑器。组件定义须写在 plugin 里，因为 plugin 在从存储加载组件之前执行（S3）。可跳转去向：BlockManager 区块库、Traits 属性面板、Style Manager、Pages、Storage Manager。

结构分区

文档级分区为"Component Definition → Component 实例(Model) → View(画布渲染)"三段。官方明确：Model/Component 是最终代码（HTML 导出）的唯一真相源，View/ComponentView 只负责在画布里预览，View 里追加的 DOM 与 async 内容不进模板数据（S3）。

列表列与筛选

内置 Component Types 按 Type Stack 顺序列出 19 类：cell / row / table / thead / tbody / tfoot / map / link / label / video / image / script / svg / comment / textnode / text / wrapper / default。识别时自栈顶向下逐个调用 isComponent，命中即停；isParsedNode 优先于 isComponent（v0.23.1 起推荐）。画布默认布局未验证。

行与批量操作

组件动作：append（支持 at 指定插入位置）、components() 读写子级、setAttributes/addAttributes、toHTML()、toJSON()、find() 查询。生命周期钩子成对出现：model.init → component:create、view.onRender → component:mount、model.updated → component:update、model.removed → component:remove。

字段名标识类型与长度精度枚举与取值口径必填 · 只读 · 默认值来源校验与唯一性展示格式
标签名tagName字符串HTML 标签，如 div / span / img选填 · 默认 divHTML 解析 / 录入须为合法标签；长度未验证画布按标签渲染

状态 × 动作（Storage Manager，S4）

状态读取项目数据保存项目数据导出 HTML/CSS

官方硬性口径（S4）："never rely on HTML/CSS as a persistence layer"——项目数据只存 JSON（含 styles、pages），HTML/CSS 是导出物，不是持久层。

交互与异常

local 存储默认用 localStorage，多项目需按 projectId 分 key；remote 存储 load 用 GET、store 用 POST（可用 fetchOptions 改 PATCH），失败可在自定义 Storage 里回退到 local（S4 给了 remote-local 组合示例）。空态、请求失败提示位置、重复提交处理均未在运行实例验证。

3.2 Puck › ComponentConfig / Data Model

入口

以 Config.components 注册区块，编辑器组件 <Puck> 与只读渲染组件 <Render> 分离（S5/S6）。页面类型为 React 可视化编辑器。外部数据源、Viewports、Localization、Feature Toggling 均为文档侧栏的独立集成项。

结构分区

三件套：fields 声明可编辑字段 → defaultProps 给插入时的默认值 → render(props) 同时用于画布预览与最终页面渲染（靠 puck.isEditing 区分）。嵌套用 slot 字段（旧 DropZone / renderDropZone 已标记废弃）。

表单字段（ComponentConfig，S5）

字段名标识类型与长度精度枚举与取值口径必填 · 只读 · 默认值来源校验与唯一性展示格式

字段定义fields对象text / number / radio / slot 等 Field 类型；radio 带 options[{label,value}]选填 · 默认空配置录入键名须与 props 对应右侧字段面板

3.3 ReactFlow › Quick Start / Core Concepts

入口

npm install @xyflow/react，引入 @xyflow/react/dist/style.css，父容器必须有宽高（S7）。页面类型为节点画布。可跳转去向：Nodes / Handles / Edges 自定义、MiniMap / Controls / Background / Panel 内置组件、Undo and Redo / Save and Restore 等示例。

结构分区

数据分区是 nodes[] + edges[] 两个平铺数组，非嵌套树；视图由 <ReactFlow> 组件承载，fitView 自适应。受控模式由 onNodesChange / onEdgesChange / onConnect 三个回调 + applyNodeChanges / applyEdgeChanges / addEdge 三个纯函数驱动；另有 Uncontrolled Flow 模式。

3.4 tldraw › Editor

入口

<Tldraw onMount={(editor)=>…}> 或 useEditor() 拿 Editor 实例（S8）。Editor 类被设计成"几乎所有能力都通过它访问"的总入口，页面类型为无限画布。

结构分区

响应式三层：Signals（响应式原语，track / useValue）→ Store（持有全部 record 的响应式数据库）→ Shapes / Bindings / Pages / Assets（文档对象）。交互层是 Tools 状态机 + Selection + Camera + Coordinates；横切能力含 History、Readonly mode、Locked shapes、Validation、Image export。

5 横向对比

行是能力维度、列是四套主对象，格填 有 / 无 / 未验证。数据来自 3.1~3.4 的字段表与文档原文，每个"有"都能回指对应小节。

差异原因：GrapesJS 与 Puck 是"页面搭建器"，产物是页面，因此有区块定义、属性面板、区块级字段；ReactFlow 与 tldraw 是"画布引擎"，产物是图 / 白板记录，因此把投入放在节点连线、吸附、事务与协同，没有区块字段与属性面板。草稿发布四家全无，是因为它们都定位为可嵌入的编辑器库，发布态属于宿主的业务域，不属于编辑器内核——这正是本项目 site-content 已经具备、无需重做的部分。

6 结论与落点

本轮修正 《独立站店铺装修可视化画布迁移-2026-11-09》 的 C1 与 R1：A 级实见显示 nav-site-ops 下已有 site-content（四态、栏目、内容类型、四端同步、历史版本），不应再新增"店铺装修"段与 site-decorate-editor 页；装修能力应作为 site-content 的编辑态升级。该报告其余结论（schema 驱动、不套 M3 视觉、复用站点商品 / 多端发布 / 成员与权限）不变。

编号判定结论落点
