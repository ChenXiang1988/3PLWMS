6 结论与落点

编号判定结论落点
C1可借鉴以 JSON 模板作为打印布局的唯一配置源，设计态通过拖拽产生 JSON，运行态用业务数据渲染 HTML；该分离方式适合避免在面单页面硬编码坐标。货主端打印能力方案；新增打印模板实体字段 templateJson、schemaVersion，落到面单/标签/箱唛模板管理方案，不直接改现有页面。
C2可借鉴将“纸张规格、元素设计、JSON 导出、预览、打印”拆为连续动作；示例同时支持预置纸张和自定义宽高。货主端模板设计页；面单、标签、箱唛模板的设计器交互与页面状态。
C3可借鉴getSimpleHtml 先产出 HTML，再由外部打印方式接管，便于把预览、下载和打印分开验收。共享打印渲染层；统一输出 html 与文件生成请求，不把 jqprint 作为后端打印队列。
C4可借鉴字段通过 options.field 绑定业务数据，示例中的 name、barcode 说明模板可复用同一数据结构。自发货单、平台备货单、打包单；字段映射登记到数据字典，禁止在模板内复制一套业务主档。
C5不跟随不把外部 jqprint 调用直接视为生产打印服务；它依赖浏览器、CSS 和当前页面资源，无法覆盖队列、重试、打印机状态和审计。货主端 owner/selfship-list、owner/*-replenish-list；打印动作应走文件生成/预览/输出状态机，生产服务另行选型。
C6不跟随不把 README 的“easy to pdf”当作内置 PDF 生成能力；官方示例主要是 HTML 生成，PDF 转换只出现在注释层。架构设计与技术选型；PDF 生成器、字体、分页、文件存储和下载权限单独评估。
C7不跟随不把平台返回的原始面单重新套用本地模板；面单来源由平台适配器决定，重排可能破坏平台要求的字段、条码或尺寸。owner/platform-adapter-list 的 labelSource；平台面单与本地模板渲染分支必须明确。
C8待定是否采用 hiprint 作为生产渲染依赖待定：当前缺 npm 包发布信息、完整 API、真实浏览器打印结果、PDF 方案、浏览器兼容矩阵和商业授权条款。决策人：技术负责人、法务、仓储业务负责人；影响打印模板管理、文件服务、打印服务和五端打印入口。

6.1 建议

编号动作前置判据
R1建立 3 个最小验证模板：热敏面单、箱唛、A4 装箱单。确认本项目字段映射、纸张尺寸和一条真实脱敏数据。三种模板均能导出 JSON、生成分页 HTML，字段缺失有可见错误，不改动业务数据。
R2在 Chromium、Firefox、Safari 各执行预览、系统打印和“打印为 PDF”。准备同一模板、同一字体、同一数据和截图/文件比对规则。页数、纸张方向、条码可读性、边距和元素坐标差异均有记录，差异超过阈值则不选 hiprint 直出。
R3向维护者或法务核实 GPL/商业授权条款及可发布方式。取得完整许可证文本、源码版本、依赖清单和商业授权报价/条款。形成书面结论：允许的部署形态、修改义务、闭源系统使用边界和归属声明。
R4先设计本项目打印状态机，再决定是否接 hiprint。确定生成、预览、下载、打印、失败、重试、过期和审计字段。模板渲染器可替换；hiprint 只承担渲染时仍能保留队列、权限和审计。
R5将 hiprint 验证落在独立试验页，不直接嵌入现有自发货或备货页。跨端联动评估打印模板实体、共享渲染层、面单来源和文件字段。试验页通过后再提出原型改动清单；现有页面不出现未验收的“打印成功”状态。
