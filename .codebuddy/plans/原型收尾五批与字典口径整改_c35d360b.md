## User Requirements

- 按上一轮确认的五批收尾计划推进；本轮确认两项决策：空抽屉补演示明细数据，旧数据字典改写成计划单口径。
- 未答项按合理假设处理：出库计划单列表的「查看工序单」保持原型示意，不做真实页面跳转。
- 每批完成都要重建五端产物、跑不带 fast 的全量验收、文档留痕并更新索引、两个自检零错误。

## Product Overview

五端可独立部署的 3PL 云仓 HTML 原型，以及配套的产品需求文档、数据字典与原型规范。本轮补齐列表行抽屉的演示内容、补上出库侧对称入口、整理页面源结构、统一字典口径，使原型打开后每一行详情都有内容、文档与现场一致。

## Core Features

- 三个列表页的行抽屉全部有明细与操作轨迹：入库计划单 8 行、收货单 6 行、商品档案 7 行，点开不再出现空态。
- 抽屉交互经过浏览器实测：打开、切页、切回、再打开、点遮罩关闭。
- 出库计划单列表新增详情抽屉，与入库侧对称；抽屉标题与明细列名逐字登记。
- 报表页与 PDA 表单屏改为调用共享组件，页面源不再手拼结构。
- 去掉页面里重复实现的兜底函数，统一使用共享实现。
- 入库通知单、出库订单两份字典改写为计划单口径：主键、状态、页面对应与示例数据统一；索引、日志、引用同步。

## Tech Stack Selection

沿用现有仓库技术栈，不引入新依赖、不建 package.json：

- 原型层：Node 原生 ESM 的 .mjs 页面模块与构建入口 `prototypes/build-app.mjs`，共享层 `prototypes/shared/{modules.json,ui.mjs,tokens.css.mjs}`，演示数据为 `prototypes/<模块>/data/*.json`，产物为五份自包含 HTML。
- 组件与外壳：复用 `ui.mjs` 已导出的 `ListPage` / `DetailPage` / `DrawerButton` / `DrawerDetail` / `ReportHero` / `StatRow` / `Block` / `ScanPage`，组件白名单由 `references/implementation.md` 管。
- 装配与验收：注册表 `modules.json` 的 `apps[].nav` 与 `pages[].app`；`node prototypes/build-app.mjs`、`--check`、`verify-delivery.mjs`。
- 文档与自检：`docs/check.mjs`、`docs/数据字典/check.mjs`，纯文本 Markdown 与索引/日志闭环。
- 浏览器实测：`playwright-cli` skill，用于打开本地产物点击验证。

## Implementation Approach

**总体策略**：按 P0 → P1 → P2 → P3 → P4 分批处理，每批独立构建与验收，避免共享层改动与其它批次互相污染。P0/P1 只动演示数据与页面源；P2 动共享层，单独一批；P4 只动 docs。

**P0 空抽屉补数据**：给 `in-plan-list.json`、`receiving-order.json`、`sku-list.json` 的 `details` 数组补齐与 `rows` 一一对应的条目（共 18 条），每条含行主键、明细行 `rows`、可选 `timeline`。页面模块已按 `details.find(x => x.主键 === r.主键)` 取数，三个页面源码不需要改。明细行字段必须与抽屉 `columns[].key` 同名，不往 `rows` 里塞展示字段。关键取舍：补数据放 `details` 而不是给每行加展示列，遵守「派生列写成纯函数、不往数据里加展示字段」；`sku-list.json` 是 `ref: skus` 引用声明，已验证 `hydrate` 会把非保留顶层键原样保留，`details` 不会在构建期丢失。补完后用 `playwright-cli` 打开 `dist/单仓端.html` 与 `dist/仓网管理端.html`，逐行走 B7：点「查看详情」→ 面板有内容 → 切到别的页 → 切回 → 再打开 → 点遮罩关闭。

**P1 出库侧对称**：`out-plan-list.mjs` 按 `in-plan-list.mjs` 同构改造，import `DrawerButton` / `DrawerDetail`，`renderPage` 返回 `{ html, overlay }`，操作列用 `DrawerButton`；`out-plan-list.json` 加 `details`。不新增注册页面条目、不改 `nav-outbound`、不加跨页跳转。抽屉标题「出库计划单详情」与明细列名先在 `glossary.md` 登记再写页面。

**P2 页面源结构整改**：先在 `references/implementation.md` 定组件契约并写进组件白名单，再在 `ui.mjs` 新增 report 外壳组件（如 `ReportPage({hero, stats, blocks})`）与 PDA 表单屏组件，最后逐页把 `renderPage` 里的手写结构替换为组件调用。分两小步：先 9 个 report 页（结构雷同、`wx-report` 外壳一致），再 PDA 相关页面；每小步各自重建五端并验收。构建期补一条断言拦截「页面源出现大段结构拼接」，否则下次还会有人手拼回去；`anti-patterns.md` 1.2 同步补判定口径。取舍：只抽重复的骨架外壳，不重写各页的指标、横条数据逻辑，避免把批次扩成全库重构。

**P3 工具函数去重**：把 `mall-price-list.mjs`、`mall-order-list.mjs`、`sla-list.mjs` 等页面里自造的 `money` / 兜底三元删掉，改 import 共享 `dash` / `n`。`labelOf` 与各页 `STATUS_META` 保留：各页状态枚举本就不同，上提要连带改数据字典枚举与二十多个页面，用户可见收益低。

**P4 字典改写成计划单口径**：这是本轮最需要明确口径的一处。现场存在同名不同层级——`入库计划单.md` / `出库计划单.md` 定义的是 L0（货主建单、仓网确认、锁库、分发，`planNo` / `planStatus`），而单仓端 `in-plan-list` / `out-plan-list` 页面是直接进仓作业的同名计划单；两份旧字典 `入库通知单.md` / `出库订单.md` 仍是 `asnNo` / `soNo` 的旧 L1 执行单口径。

**决策：保留两份文件与实体清单条目，只改写正文口径，不删文件、不新建实体、不重命名文件**。理由：一是字面贴合「改写」；二是 `docs/数据字典/check.mjs` 校验实体清单与链接闭环，删实体要连带删索引行、samples 和所有引用，风险远大于收益；三是保留「L0 委托层 / 单仓执行层」两层业务语义，避免把两个层级压进一份字典。具体改写：去掉 `入库通知单.md` 第 3 行「保留作字段历史参考」的过时注记，改为与 L0 计划单字典的分工说明；实体定义改为「计划单确认分发后在单仓形成的执行单」；业务引用主键统一 `planNo`，删除 `asnNo` / `soNo`（仓内执行单号若需要，作派生列不进字段表）；状态枚举统一取 `glossary.md` 的计划单状态 5 值与作业状态 5 值，删掉旧的入库 6 态、出库 7 态；「原型衔接」章节的页 key 改为现场页 `inbound/in-plan-list`（含详情抽屉）、`inbound/receiving-order`、`inbound/putaway-order`、`outbound/out-plan-list`（含详情抽屉）、`outbound/wave-list`、`outbound/picking-order`、`outbound/check-order`、`outbound/handover-list`，列名逐字取 glossary。同步 `docs/数据字典/index.md` 说明列与最近更新、`docs/数据字典/log.md` 追加记录、samples 示例数据字段，以及引用旧字段的 `工序单.md`、`时效协议.md`、`商城订单.md`、`承运商主档.md`；`docs/数据字典/log.md` 的历史条目不回改。`docs/产品需求/计划单与时效协议方案.md` 与 `单仓端三模块设计方案.md` 补一句 L0 / 单仓执行层的分层说明。

**Performance & Reliability**：补 18 条明细只增加构建期静态数据，单端产物增量约几十 KB，仍远小于 100 KB；`hydrate` 与 `details.find` 都是线性查找、数据量个位数到十几条，无热点。抽屉面板按 `pageId + rowKey` 双键定位，构建期 `[抽屉]` 断言保证每个入口都有面板；补数据后再用浏览器实测覆盖 B7。P2 抽组件会减少重复 HTML 拼接，产物体积略降。

**Avoiding Technical Debt**：全部复用现有组件、data-* 契约与附录式 `details` 结构；新组件先改规范层再改实现层；不新建文件、不改 `check.mjs` 逻辑来迁就改动；P1 的「查看工序单」保持 toast 示意，不碰「页头页签按分组成组」口径。

## Architecture Design

现有架构不变：源按模块目录组织，端由 `modules.json` 在构建期聚合；规范层 `references/` 管上限与文案，`prototypes/shared/` 管取值与结构，`modules.json` 只管装配。本轮改动沿三条独立链路推进，互不交叉：

1. 数据链路：三个 `data/*.json` 的 `details` → 页面模块 `renderPage` → `DrawerDetail` overlay → `build-app.mjs` 挂 `.wx-overlay` → 产物。
2. 组件链路：`references/implementation.md` 契约 → `ui.mjs` 新组件 → 各页面模块替换 → 构建期断言 → 五端产物。
3. 文档链路：两份实体字典正文口径 → 索引/日志/示例/引用字典 → 两个自检脚本闭环。

P0、P1、P3、P4 不动共享层，P2 单独一批动共享层并全量重建，避免批次之间互相覆盖产物。

## Key Code Structures

`details` 条目形状是 P0 与 P1 共用的数据契约，页面模块按行主键查找，字段名必须与抽屉 `columns[].key` 一致：

```
details 条目（与列表 rows 中某一行按主键同值匹配）
- 行主键字段：planNo / processNo / skuCode，字符串，值等于该行同名字段
- rows：明细行数组，每个对象的 key 与抽屉 columns[].key 同名
- timeline：可为空数组，元素为 { time, text, operator }，均为字符串
```

不新增类型定义或导出接口；`renderPage` 继续返回字符串或 `{ html, overlay }`，`DrawerButton` / `DrawerDetail` 的入参保持现状。
