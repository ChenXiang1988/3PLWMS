## 用户需求

检查 `.codebuddy/rules/` 下 5 条规则能否合并，给出评估与方案。评估已完成并确认：按场景合并不划算，改为做跨文件去重与引用方式整改；本轮实施该整改。

## 体检结论（已确认）

- 5 条规则共约 21.2 KB，仅「工作前读规范」（2.8 KB）为 alwaysApply，其余 4 条按需生效。
- 4 条按需规则的触发场景正交（改原型 / 画图 / 写调研），唯一贴近的「界面文案纪律 + 跨端联动确认」合并会破坏文案规则的可移植性（其第 5 节自称可整节替换、正文不动）；「流程图规范 + 调研颗粒度」合并会让 12 KB 在每次画图时全量加载；「工作前读规范」并入 CODEBUDDY.md 省不到实际体积，还会丢掉规范缺失/冲突时的判定条。
- 真正的重复不在规则之间，而在规则与外部文件之间，共 4 处。

## 本轮涉及的功能内容

1. **常驻规则瘦身**：`工作前读规范` 的表格把目标规则的核心要求又摘了一遍（含与 huoling-proto SKILL 重复的「第 0 步挑卷」细则），4 行约 520 字压到约 180 字，只留「任务 → 读哪个文件」和一句非显然提示，省下的常驻体积每轮对话都兑现。
2. **调研规则去重**：`调研颗粒度` 第 7 节的八节枚举与 `research-report` 技能「八节骨架」逐条一致，规则侧收敛为指向技能，保留项目级内容（目录、命名、24 小时窗口、meta、截图、登记与校验），第 7 节编号与标题不动。
3. **索引去重**：`docs/index.md` 第 6 条把调研要求又抄了一遍，压成存放约定 + 指针。
4. **引用方式整改**：5 处按「第 N 条 / 第 N 节」引用的地方改为按标题引用，避免后续增删条目错位。
5. **留痕与验收**：`docs/log.md` 追加记录，两个文档校验脚本零错误。

## 边界

- 不改规则的文件名、目录名、frontmatter 的 alwaysApply 与 description 语义。
- 不改 `huoling-proto/SKILL.md` 的三处规则摘要（技能内自包含，规则未加载时需要），也不删其中的字数。
- 不改 `docs/check.mjs` 的 `SURVEY_SECTIONS` 与 `check-report.mjs` 的 `SECTIONS`（脚本常量，属执行校验）。
- 不动 `prototypes/`，不触发跨端联动评估，不重建产物。

## 预期效果

规则总数仍为 5 个、触发方式不变，跨文件重复的约 660 字只留一处；后续任何规则增删条目，引用不会错位；所有校验脚本通过。

## 改动性质

纯文本与文档结构调整，无代码逻辑改动、无新依赖。改动面为 3 个规则/文档文件 + 3 个引用方文件 + 1 个日志文件，全部在既有规范体系内，不引入新模式。

## 实施策略

1. **只删冗余，不删信息**。每条被压缩的内容都必须先确认「同一信息在另一处仍存在且更容易维护」，删的是副本而不是知识。指针一律带文件路径，保证可追溯。
2. **保编号、保标题**。`调研颗粒度` 第 7 节「交付物」、`跨端联动确认` 第 3 节「清单怎么写」的编号与标题是 3 处外部引用的锚点，本轮只改被引用话语的表述，不动节本身。
3. **引用改锚点方式而非改目标**。5 处「第 N 条 / 第 N 节」统一改为「某文件·某标题」形式，消除序号漂移风险。
4. **验收前置明确**。`docs/check.mjs` 只校验 `index.md` 的三个必需章节（使用规则 / 日志管理 / 分类与文档）与分类表字段，不校验使用规则条目编号，因此改写第 6 条安全；log 记录引用文档相对路径时须已在 `index.md` 登记，故规则类改动沿用历史第 47 行的「项目规则｜修改」写法，不写 .md 路径。
